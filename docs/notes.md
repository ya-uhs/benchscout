# benchscout 作業メモ

作業の記録:今どこまでできているか、次に何をするか、実機で何が分かったか、設計レビューで何を指摘し何に落ち着いたか。
**何を作るか・なぜそうするか(設計と決定)は [design.md](design.md)。** ここで見つけたことから方針が決まったら、その決定だけを design.md の §12 決定ログに短く書き、経緯はここに残す。

参照の書き方:実機で学んだことの項目は「実機 21」、設計レビューの指摘は「レビュー U9」(R・S・T・U は 1〜4 回目のレビュー)。

## 現状(旧 design.md §11、2026-11-02 時点)

### できている

- **輪**:受信箱の質問 → エージェントを起こす(Claude Code は `claude -p`、ほかは ACP)→ 選んだ機器を見張る(開いて安全で
  なければ benchscout が聞く)→ クラッシュ・ポートの消失に気づいて起こす(コンピュータのスリープは記録だけ)→ 記憶
- **安全**:ブローカー、影響の伝播、承認(メモリ上、人が決めるまで待つ、範囲と期限付き)、機器のロックと OS の排他、
  制御の経路とエージェントの経路の分離、慎重な既定値(同梱データを消しても緩まない)
- **名前**:USB の名乗り、`*IDN?`、openFPGALoader の DB、エージェントの引用の照合(`bench_identify`)だけ。コードに機器の知識なし
  (製品のコード全体をテストで見張る。見たことのない機器のベンチでもテスト)
- **記憶**:自動で書く。安全を緩めるものだけ人が確認(確認待ちは再起動後も出し直す)。機器のコマンド(`serial.command`)
- **書き込み**:ESP のフラッシュ、FPGA の SRAM とフラッシュを DANGEROUS の操作としてデータで定義。外部の道具は初めて使うときに
  公式のリリースから取る(版と SHA-256 を固定、承認カードに表示。裏で進め、受信箱に進み具合)。openFPGALoader はコアに同梱。
  同梱していない道具(ベンダー公式の書き込みツールなど)はエージェントが提案し、人が受信箱で確認して加える(`bench_define_tool`)
- **承認の幅**:1 回 / この操作(SCPI は人が見たその命令)をセッション中 / この機器では今後も(SCPI)/ このセッション中はすべて
  (元に戻せない操作は除く)。SCPI は規格が決めた命令だけを名前で判定(レビュー U9、U12)
- **Windows**:Windows 11 ARM64 の VM で実機(ESP32-S3)を動かし、書き込みまで通った(実機 22)。ドライバが無い・違うときは、
  どのインターフェースに何が要るかを受信箱とレポートで言う
- **画面**:VS Code 拡張の受信箱(日本語/英語、機器ごとの「手放す / 使う」)、Workspace Trust、.vsix にコアを同梱(4 種)
- **検査**:Python 166 件・拡張 32 件のテスト(安全の門と SCPI はランダムな入力の性質テストも)、ruff、mypy(3 OS)、
  3 OS の CI で本物の VS Code を使う通しの確認(`npm run e2e`)、固めたコアに対するテスト(配布先 4 種)

### まだ

「次にやること」を見る。Windows での Tang Nano の JTAG(Zadig で WinUSB を入れてから)、Linux の udev の規則、測定器の値の範囲、
パネルの記憶ビュー、配布の前の Anthropic への確認。

**受け入れ試験**(これが通れば「寄せ集めではない」と言える):testbench の ESP32 で `panic` を起こしたとき、人が何も入力しなくても、

## 実機で学んだこと(旧 design.md §10)

模擬データでは一つも出なかったものばかり。実機の出力は `fixtures/real/` に保存し、テストで再現する。

1. **ネイティブ USB の ESP32-S3 は、開いた直後に DTR/RTS を下げるとリセットされる**(macOS)。開き直しても毎回。
   線を上げたまま開くとリセットされず読めた(2 回観察)。→ 開き方をポートごとに持つ(今は同梱データ、移行後は記憶)
2. **リセットや再列挙でポートが消える。** 戻ってきたら開き直して聞き続ける(最大 2 回)。諦めても読めた分は返す
3. **VISA の一覧にシリアルポート(`ASRL…`)も混ざる。** そこに `*IDN?` を送ると未知の UART にバイトを書くことになる → ASRL は VISA 側で扱わない
4. **引数付き SCPI クエリ**(`MEAS:CURR? CH1`)を書き込み扱いしていた → コマンドのヘッダで判定
5. **USB に出てこないものはソフトからは何も見えない**(Tang Nano が見えない原因は充電専用ケーブルだった)→ skill に「疑う順番」
6. **Sipeed の BL702 は FT2232H のふりをする**(0403:6010)。シリアル番号 `FactoryAIOT Pro` は全個体で共通
7. **自前の IDCODE 表が間違っていた**(0x0100481B は GW1N(R)-9C)→ 外部ツールの DB を使う(層 1)。自前の表を持つ危うさの実例
8. **MCP クライアントは中継を最小限の環境変数で起動する**(`TMPDIR` がない)→ コアと中継が合わせる場所は環境変数に頼らない
9. **`serial.listen arg=9600` を 9600 秒と読んでいた** → 操作の引数に型と範囲を付けた
10. **Tang Nano のファブリック UART の無音は、元のビットストリームが何も出していなかったため**(テスト用ビットストリームで `hb` とバナーが出た)
11. **`panic` は `abort()` とバックトレースを出し、ROM のリセット理由は `RTC_SW_CPU_RST`**(Guru Meditation の行は出ない)。
    → ログの書式を表で持つと漏れる実例。解釈はエージェントの仕事(層 4)、注意すべき行の形は記憶へ
12. **PlatformIO 同梱の esptool.py v4.5.1 は、ESP32-S3 の USB-Serial/JTAG でスタブ起動直後に止まり書けなかった。** esptool v5.6.0 では書けた
13. **Claude Code の CLI は、承認待ちの呼び出しを 60 秒・95 秒とも切らずに待った。** ただし結果に承認の情報がないと、
    「承認なしで実行された」と利用者に伝えてしまった → 結果に「人が承認した、何秒待った」を含める
14. **再スキャンで、それまでに分かったことが消えていた** → 記憶の必要性の実例(design.md §6)
15. 費用:最初の報告をエージェントにやらせると 1 回 0.16〜0.32 ドル → 一覧は LLM なしで出す
16. **自律の輪が実機で回った**(2026-11-01、testbench の ESP32-S3、Copilot CLI over ACP):人が ESP32 を選んだあと、`panic` を起こすと、
    benchscout が見張り中のログで `abort()` に気づき、人の操作なしに Copilot を起こした。Copilot はログを読み、`reset=PANIC`、
    `RTC_SW_CPU_RST`、心拍の再開を引用し、「根本原因は ELF なしでは特定できない」と限界を示して次の手(PC のシンボル化)を出した。
    1 回のクラッシュが複数の警告の行(abort とバックトレース)になり、二重のカードが出た → 起こした直後の同じ機器の警告は記録だけにした
17. **受け入れ試験が実機で通った**(2026-11-01、ESP32-S3 + Copilot CLI):人は ESP32 を選びカードに答えただけ。`panic` の後、benchscout が
    気づいて Copilot を起こし、Copilot はログを読み、`ESP-ROM:esp32s3-20210327` を引用して `bench_identify` で ESP32-S3 と特定(照合済み)、
    `abort()` の行を注意すべき行として記憶し、次の手を `ask_user` で聞き、報告した。コアを立ち上げ直した新しいセッションでは、LLM なしの
    最初の質問にもう「ESP32-S3」と出た。途中で見つけた問題:拡張が新しい道具(`bench_recall`)を benchscout のものと認識せず人に回した
    (→ 道具の一覧をテストで relay と突き合わせる)、エージェントがログをシェルで読もうとした(→ `bench_log`)。報告に「再起動を繰り返している」
    という言い過ぎが 1 つあった(実際は 1 回)
18. **VS Code の中で通しで動いた**(2026-11-01、VS Code 1.140、macOS arm64)。利用者の VS Code に触れないよう、分離したプロフィール
    (専用の設定と拡張のフォルダ)に配布用の .vsix を入れ、Chrome DevTools Protocol で画面を撮り、DOM を読み、ボタンを押して確かめた
    (`npm run ui-check`)。分かったこと:
    - **選んだ機器を見張れていなかった。** 記憶のない ESP32-S3 は開くと DISRUPTIVE なので見張りが始まらず、クラッシュに気づけない。
      エージェントは「listen してよいか」を `ask_user` で聞き、そのあと `bench_do` の承認でもう一度聞く、二重の確認になった
      → 開いて安全に見張れないポートは、benchscout が自分で「見張りますか」を承認カードで出す。SKILL に「not SAFE はまず `bench_do`、
      カードが質問になる」「承認待ちと言うのは approval_required が返ったときだけ」を足した(エージェントは来ていない承認を「待っている」と書いた)
    - **エージェントを選ぶ前に機器を選ぶと「起こせない」と出た** → 選ばれるまで依頼を待たせ、選ばれたら起こす。エージェントのカードは上に固定
    - **拡張の経路では skill がフォルダに置かれていなかった**(`benchscout setup` を通る経路だけ置いていた)→ 拡張がコアに `setup --skill-only`
      を頼む。直した後は Copilot が「Using skill: bench-expert」と読み込み、二重の確認もしなくなった
    - 2 回目以降の途中経過が最初の報告カードに書かれていた。報告の Markdown が記号のまま出ていた。ボタンと時刻が 1 文字ずつ折り返していた
    - .vsix で入れた同梱のコアは実行権限が残り、ブラウザで落とした(quarantine の付いた).vsix からでも展開したファイルには quarantine が
      付かず、ad-hoc 署名のまま Gatekeeper に止められず動いた
    - VS Code の MCP の一覧に、拡張が登録した benchscout が出て、起動すると 10 の道具を見つけた。サインインした後、VS Code の Copilot Chat
      (エージェントモード)が skill を読み、`bench_scan` を呼んで(VS Code 自身のツール確認を経て)2 台を答え、「どちらもまだ選択されていない」
      と選択の状態まで正しく伝えた
    - 実機(Tang Nano 9K)でも、パネルで選ぶ → ファブリック UART を見張る → Copilot が `bench_log` で `hb` を読み、IDCODE を openFPGALoader の
      DB で引き、`ask_user` で次の方向を聞き、報告する、まで回った
    - VS Code の IPC ソケットはプロフィールのフォルダに作られ、パスが 103 文字を超えると起動しない
19. **CI を初めて Windows で回した**(2026-11-01、GitHub Actions)。分かったこと:Windows の npm は CLI を `.cmd` で入れる(`copilot.cmd`)ので、
    `.exe` だけを探していた拡張はエージェントを見つけられず、見つけても `.cmd` はシェルなしでは起動できない → cross-spawn(npm や execa が
    使う)で起動し、引数(MCP の設定の JSON)を cmd.exe 向けに正しく渡す。npm は Windows ではスクリプトを cmd.exe で動かすので
    `$VSCE_TARGET` が展開されない → vsce の API で .vsix を作る。macOS の runner の python.org 版 Python は Framework 形式で、固めたコアに
    シンボリックリンクが入り .vsix(zip)に入らない → uv が管理する Python で固める。テスト・.vsix 作りとも 3 OS で通った。Windows の実機は未確認
20. **書き込みが実機で通った、VS Code の受信箱から**(2026-11-01、.vsix で入れた拡張、承認は受信箱のカード):ESP32-S3 のアプリ領域
    (`esptool.write_flash`、esptool 5.6.0、`0x10000`)はハッシュ照合まで成功。書き込みの間は見張りを止めてポートを渡し、終わったら戻し、
    新しいファームの起動行と 1 からの心拍が見えた。Tang Nano 9K のフラッシュ(`fpga.write_flash`、openFPGALoader `--write-flash`)は
    CRC 照合まで成功し、「設定からの秒数」の心拍が 1 から数え直した(フラッシュから設定し直された)。分かったこと:
    - パネルが英語だった:VS Code に言語パックがなく表示言語は英語、OS は日本語 → 設定 `benchscout.language`(auto: VS Code が英語なら
      OS の言語)。日本語の利用者の多くは VS Code を英語のまま使う
    - ESP32-S3 の「開いても安全」は記憶になかった(「消えなかった」が 1 回だけ)。見張りを人が許可 → 2 回目の観察 → benchscout が
      「開いても安全として扱いますか」を人に出した(設計どおり)
    - エージェントの `request_devices` が、人が許可したのに `"selected": []` を返した(選択より先に呼び出しが起きていた)→ 答えに沿って
      動いてから起こす
    - 承認カードのフラッシュの対応表が 10 進(`65536`)で出ていた → `0x10000:firmware.bin` の形に
    - 外部ツールが機器を持っている間に出た行(FPGA の起動バナー)はログに残らない。ツールが手放してから見張りを戻すまでの間は聞けない
    - 「開いても安全として扱いますか」のカードが、ウィンドウを読み込み直すと消え、確認待ちのまま宙に浮いた → 確認待ちの記憶は、つながって
      いる機器のものだけスキャンのときに出し直す(1 セッション 1 回)。その本文(benchscout 自身の文)もパネルの言語で出す。ステータスバーの
      「確認待ち」にも数える
21. **「リセットしました」が一晩じゅう続いた。原因は機器ではなく Mac のスリープだった**(2026-11-01〜02、ふたを閉じてバッテリーで放置)。
    DarkWake のたびに USB のポートが消えて戻り、benchscout はそれを「リセット」と呼んでエージェントを起こしていた。両方の機器のカウンタは
    一度も 1 に戻っておらず(FPGA の「設定からの秒数」、ESP32 の `n=`)、エージェントも「カウンタは続いている」と見抜いていたが、Mac の
    スリープは知りようがない → 見張りが、スリープを数えない時計(`time.monotonic`)と数える時計(`time.time`)のずれでスリープを検出し、
    その前後のポートの消失は「Mac のスリープで切れ、開き直した」と機器ごとに 1 枚にまとめて記録するだけにする(エージェントは起こさない)。
    それ以外でも「リセット」とは言い切らず「ポートが消えて戻った(リセットか USB の切断)」と言う。Windows では検出しない(時計の性質が違う)

22. **Windows 11 ARM64 で実機を動かした**(2026-11-02、UTM の VM に ESP32-S3 と Tang Nano 9K を USB で渡した)。テスト一式と、本物の VS Code(win32-arm64)での受信箱の通しの確認は通った。実機で分かったこと:
   - **子プロセスが制御チャネルを受け継ぐと止まる。** コアのメインスレッドは標準入力(制御チャネル)を読み続けている。Windows では、読み取りが保留中のパイプを受け継いだ子は、その読み取りが終わるまで待つ。`esptool version`(版の確認)が次の制御の行まで 160 秒止まり、エージェントの呼び出しが時間切れになった。すべての子プロセスに空の標準入力を渡す(テストで見張る)。時間切れの道具はプロセスの木ごと止める(PyInstaller で作った道具は子が出力のパイプを握ったまま残る)
   - **標準入出力の文字コード。** パイプは cp1252 になり、`scan` の表示で落ち、拡張から来る日本語の返事が化けるか、cp1252 に無いバイトでコアが止まった。3 つとも UTF-8 にした
   - **名前は機器から。** WMI の名前はドライバのもの(「USB Composite Device」「(Standard USB Host Controller)」)で、それを USB のディスクリプタとして出していた。ハブ経由で機器自身の文字列ディスクリプタを読む(USBView と同じ方法)。読めないときは Windows がバスから控えた製品名。ESP32-S3 は macOS と同じ「Espressif USB JTAG/serial debug unit」になった
   - **ドライバの無い機器。** Tang Nano の FT2232 は Windows にドライバが無く(2 つのインターフェースとも)、ポートができず一覧から消えていた。一覧に出し、どのインターフェースに何が無いか、何を入れれば使えるか(シリアルはメーカーのドライバ、libusb の道具は WinUSB)を言う。ドライバが無い機器は文字列ディスクリプタにも答えない(Windows が控えたシリアル番号だけ返る)ので、メーカー名で照合するボードの配線データはドライバを入れるまで当たらない
   - ESP32-S3 は開いてもリセットしなかった(Windows の usbser)。esptool 5.6.0 は初回に取得(win32-x64 をエミュレーションで実行)、chip-id とアプリ領域の書き込み・照合が通った。書き込みの間は見張りを外し、終わって戻すので、起動直後の 1 行目は取りこぼす
   - Tang Nano の JTAG(同梱の openFPGALoader):利用者が VM で Zadig を使ったが、Windows が WinUSB のパッケージを拒否した(setupapi.dev.log:「Driver package signer is not trusted by system, and Code Integrity is enforced」0xE0000243)。Zadig は自己署名のカタログで入れるので、Arm の Windows やコードの整合性の検査が強制された PC では通らないことがある。x64 の実機では未確認。そういう PC ではベンダー公式の書き込みツール(メーカーのドライバで動く)を `bench_define_tool` で加えるのが道。受信箱のカードとレポートにそう書いた。FT2232 のもう一方(UART)も FTDI のドライバが入らず(Windows Update が ARM64 用を配らなかった)
23. **同梱していないベンダーの道具を、エージェントの提案で実機に通した**(2026-11-02、macOS、ESP32-S3)。利用者が PlatformIO でEspressif 版の OpenOCD(v0.12.0-esp32-20230419)を入れ、エージェント役が ESP-IDF の文書(「openocd -f board/esp32s3-builtin.cfg」、実行例のログに「Core was reset」)を根拠に `bench_define_tool` で提案(影響度は DISRUPTIVE)。人の確認で作業フォルダの知識に入り、承認カードには同じチップのシリアルポートへの影響も出た。実行で JTAG の TAP 2 つ(IDCODE 0x120034e5、Tensilica)を読めた。
   - 見つかったこと:人が「追加する」を押した瞬間にエージェントの呼び出しへ「追加済み」が返り、知識の書き込みと読み直しの前だったので、次の `bench_do` が「その操作は無い」と断られた。書き込みと読み直しのあとで返すように直し、同時に動く形のテスト(古い作りでは 3 回とも落ちる)を足した。前のテストは人の決定とエージェントの問い合わせを順に呼んでいたので、この競合が出なかった

#### R3 の詳細:承認は人の経路からだけ

参考:**ssh-add -c + ssh-askpass**、**gpg-agent + pinentry**(確認は頼んだ側が操作できない別の経路で人に求める)。

- エージェントの経路(MCP の中継)はツールを呼ぶだけで、承認する手段がない。制御の経路は、コアを子プロセスとして起動した拡張だけが持つ
- 承認の状態はコアのメモリだけ。記録(監査ログ)はファイルに追記するが、書き換えても承認にはならない

**脅威モデル**:守る相手は、エージェントの **間違いと行き過ぎ**(勝手に承認する、ファイルを書き換える、ポートを直接開く)。
同じ利用者の権限で意図的に攻撃してくるプログラムは対象外。DANGEROUS な操作には、将来 OS の確認(Touch ID など)を挟む余地を残す。

**残る穴**:選んでいない機器は OS の排他がかかっていないので、エージェントがシェルから直接開けてしまう(instructions / skill の指示だけ)。
エージェントが自分で `benchscout core` を起動して制御の経路に入力を流し込むのは意図的な回避なので対象外(Claude Code 向けの設定では
`benchscout` を Bash から呼ぶことを deny にしておく)。

#### R8 の詳細:範囲と期限付きの許可

- **DISRUPTIVE な操作に限り**、(操作, 口) に対して「このセッションの間」または「N 分間」の許可を出せる
- **DANGEROUS な操作は**、(操作, 口, 引数) に紐付いた1回限り
- 範囲付きの許可も、出せるのは人だけ。選択から外れた機器、セッションの終了、期限切れで消える

### 5回目(2026-11-02):設計思想の根幹から見直し(「FPGA は openFPGALoader 決め打ちでは?」)

design.md §0〜§5、§17 を読み直し、原則ごとに実装を突き合わせた。

**沿っていたこと**:役割分担(benchscout に LLM 機能なし。正体の特定とログの解釈はエージェント)、入口は MCP だけ、承認は人の経路だけ
(テストで確認)、慎重な既定値と「同梱データを消しても安全側にしか倒れない」、記憶(自動で書き、安全を緩めるものだけ人)、受信箱、
自律の輪(見張る → 気づく → 起こす → 調べる → 残す)。コードに機器の名前はない(テストで見張っている)。

**ずれていたこと**:

| | 指摘 | 結論 |
|---|---|---|
| V1 | 道具の選択が benchscout 側に固定されていた。FPGA の書き込みは openFPGALoader、ESP は esptool の定義しかなく、それらが対応しない部品では、エージェントが正しい道具を見つけても benchscout の門を通して使う道がなかった。「どの道具で扱うか」は知識(エージェントの仕事)なのに、同梱データ(benchscout の仕事)として持っていた | `bench_define_tool`(エージェントが提案、人が確認、作業フォルダの知識へ)。design.md §3、§5 に原則として書いた |
| V2 | データの無い USB 機器は一覧に出なかった(シリアルポートかデータがある機器だけ)。シリアルポートの無い書き込み器(USB-Blaster、Platform Cable)はエージェントにも見えず、V1 の提案もできなかった。原則 1「列挙し、生の手がかりを取る」と、§2「初めて見る機器は VID:PID と名乗りで十分」に反していた | ハブを除くすべてを手がかりとして見せる。データの無い機器は「ほかの USB 機器」として分け、受信箱では件数だけ出す |
| V3 | 探す外部ツールの名前の一覧がコードにあった(使う定義の無い openocd や probe-rs まで「入っていない」と出していた) | データ(道具の操作の定義と USB の `tools`)から引く |

**なぜそうなったか**:

1. **設計の穴**:§4 は「外部ツールの操作はデータで定義する。コードを変えずに足せる」、§5 は「調べものはエージェント」と書いていたが、
   知らない部品のために **誰が** 道具の定義を足すのかを決めていなかった。実装はその穴を「同梱データ」で埋めた
2. **目の前のベンチに合わせた**:ESP32-S3 と Tang Nano で必要になるたびに、その道具とその見え方を同梱で足し、「このベンチで動く」で
   確かめていた
3. **見張っていたのは安全の一般性だけ**:見たことのない機器のベンチのテストは「慎重になるか」「名前を付けないか」を確かめていたが、
   「そのうえで仕事ができるか」(見えるか、道具を持ち込めるか)は確かめていなかった。だからずれがテストに出なかった

**再発を防ぐ形**:「同梱データを消しても安全側にしか倒れない」の対として、「同梱の道具の定義を消しても、知らない書き込み器が見え、
エージェントが道具を持ち込み、人の確認のあと門を通して使える」をテストにした(`test_without_any_shipped_tools_the_agent_can_still_bring_one`)。
