**何を作るか・なぜそうするか(設計と決定)は [design.md](design.md)。** ここで見つけたことから方針が決まったら、その決定だけを design.md の §12 決定ログに短く書き、経緯はここに残す。

## 現状(2026-11-09、監査 2026-11-07 と使い勝手の見直しの後)

### できている

- **エージェントが持ち込む接続先・道具・観察**: `bench_register_resource` で不透明な接続先をセッションへ登録し、
  人が選択した対象に `bench_run` でスクリプト/CLI を実行する。コアに機器・プロトコル・Codec の実装を加える必要はない。
  引数・対象・入力ファイルのハッシュ・期限を承認に結び付ける(1 回、または同じ中身の間のセッション中)。複数対象を一括占有し、既存の監視を停止して渡す。
  stdout/stderr はバイナリ保存。`observe` の出力通知は意味を付けずエージェントを起こす。`bench_job` とパネルから停止でき、
  選択解除・切断・セッション終了でも停止する。プログラムは利用者権限で動く信頼対象で、OS サンドボックスではない。

- **輪**:受信箱の質問 → エージェントを起こす(Claude Code は `claude -p`、ほかは ACP)→ 選んだ機器を見張る(開いて安全で
  なければ benchscout が聞く)→ クラッシュ・ポートの消失に気づいて起こす(コンピュータのスリープは記録だけ)→ 記憶。
  挿抜にも気づく:新しい機器は受信箱で「調べる?」、選んだ機器が抜けたら知らせ、戻れば見張りを再開(許可は取り消す)
- **安全**:ブローカー、影響の伝播、承認(メモリ上、人が決めるまで待つ、範囲と期限付き)、機器のロックと OS の排他、
  制御の経路とエージェントの経路の分離(コアと中継は利用者の鍵を互いに示す)、慎重な既定値(同梱データを消しても緩まない)
- **名前**:USB の名乗り、`*IDN?`、openFPGALoader の DB、エージェントの引用の照合(`bench_identify`)だけ。コードに機器の知識なし
  (製品のコード全体をテストで見張る。見たことのない機器のベンチでもテスト)
- **記憶**:自動で書く。安全を緩めるものだけ人が確認(確認待ちは再起動後も出し直す)。機器のコマンドは `serial.send` に統合。
  機器ごとの記憶と作業フォルダの構成・配線の記憶を分け、覚えた `inside` を影響のグラフに反映する。保存形式は TOML
- **書き込み**:ESP のフラッシュ、FPGA の SRAM とフラッシュを DANGEROUS の操作としてデータで定義。外部の道具は初めて使うときに
  公式のリリースから取る(版と SHA-256 を固定、承認カードに表示。裏で進め、受信箱に進み具合)。openFPGALoader はコアに同梱。
  同梱していない道具(ベンダー公式の書き込みツールなど)はエージェントが提案し、人が受信箱で確認して加える(`bench_define_tool`)
- **承認の幅**:1 回 / この操作(送信は人が見たその命令)をセッション中 / この機器(全個体が同じ番号の型は、1 台だけの間はこの型)
  では今後も / このセッション中はすべて(元に戻せない操作は除く)。戻せないかもしれない操作でも、同じ中身のプログラム、データが
  許す書き込み(同じ道具・同じ機器)、承認した値までの出力の設定はセッション中の許可を選べる(design.md §12 2026-11-08)。
  SCPI は規格が決めた命令だけを名前で判定(レビュー U9、U12)
- **Windows**:Windows 11 ARM64 の VM で実機(ESP32-S3)を動かし、書き込みまで通った(実機 22)。ドライバが無い・違うときは、
  どのインターフェースに何が要るかを受信箱とレポートで言う。Tang Nano(FTDI の ARM64 ドライバ)は COM ポートのチャネルを
  Windows の機器の木から読み、Linux と同じ形になる(2026-11-08、記録 fixtures/real/windows_arm64_tangnano_*)
- **画面**:VS Code 拡張の受信箱(benchscout の文は英語、エージェントは利用者の言語で答える。機器ごとの「手放す / 使う」)、Workspace Trust、.vsix にコアを同梱(4 種)
- **構造**:プロトコル・操作・配線・ログの規則・アクセス条件の置き場所を統一(レビュー 9)。任意の通信方式を MCP が扱えるという意味ではない
- **エージェント**:拡張のテストの代わりのエージェントは、本物の `claude -p` と Copilot CLI の記録を再生する(fixtures/real)。
- **検査**:2026-11-08 の時点で Python 321 件成功・1 skip(Windows VM で 317 件成功)、拡張 40 件、VS Code の通し確認。
  レビュー 9 完了時の記録は Python 234 件成功・拡張 36 件成功・VS Code の通し確認・CI 成功。
  安全の門の性質テストと構造テストがある。3 OS の CI と配布先 4 種の凍結版検査は実行経路があるが、変更のたびにすべてを
  再実行した意味ではない。今回の引継ぎ後の検査は末尾に記録する

### 2026-11-04: ハーネスの共通実行経路

- `resources.py` はセッション内の不透明な接続先登録のみ。`execution.py` は実行計画・入力ハッシュ・プロセス・生バイト成果物。
  broker が選択と承認を確かめ、対象をまとめて占有し、内蔵監視と受け渡す。プロトコルや機器名による分岐は追加していない。
- 新しい経路は MCP から使え、拡張の承認カードと実行中の停止カード、観察通知につながる。skill と設計書も、エージェントが
  道具と通信方法を持ち込む責務に合わせた。以前からの作業中ファイルと testbench は保持し、実機操作・commit・push・CI 起動はしていない。
- 検証: Python 全体 247 成功・1 skip、拡張 37 成功、mypy(30 files)・Ruff 成功。追加したローカルプログラムの検査は、
  バイト保存、承認の一回性とファイル変更、複数対象、既存監視との排他、選択解除/セッション終了/手動停止、期限、出力量、終了コード。
  実コアと拡張を使うテストで、未知接続先→承認→観察通知→パネルで停止まで確認した。
- VS Code の隔離 fixture E2E は初回に既存のクラッシュ通知待ちがタイムアウト。再実行は、実行中のログに出力が届いていることを
  確認し、全項目成功。初回の原因は特定できておらず、安定性の未検証点として残す。検証 VSIX は checkout のコアを明示して使った。
  同梱の凍結コアは再ビルドしていないため、今回の VSIX を更新済み配布物として扱わない。
- 制約: Windows/Linux 上の新経路の実動作は今回未検証。子プロセス群の停止は best effort で、detach/daemon 化は禁止。
  入力ハッシュの再確認は隔離や完全な依存解析ではなく、アドレス別名や申告外アクセスも検出しない。出力量制限は定期確認なので超過しうる。
  エージェントに渡したコードを信用する境界を設計・ツール説明に明記した。

## 実機で学んだこと(旧 design.md §10)

模擬データでは一つも出なかったものばかり。実機の出力は `fixtures/real/` に保存し、テストで再現する。

1. **ネイティブ USB の ESP32-S3 は、開いた直後に DTR/RTS を下げるとリセットされる**(macOS)。開き直しても毎回。
   線を上げたまま開くとリセットされず読めた(2 回観察)。→ 開き方をポートごとに持つ(今は同梱データ、移行後は記憶)
2. **リセットや再列挙でポートが消える。** 戻ってきたら開き直して聞き続ける(最大 2 回)。諦めても読めた分は返す
3. **VISA の一覧にシリアルポート(`ASRL…`)も混ざる。** そこに `*IDN?` を送ると未知の UART にバイトを書くことになる → ASRL は VISA 側で扱わない
4. **引数付き SCPI クエリ**(`MEAS:CURR? CH1`)を書き込み扱いしていた → コマンドのヘッダで判定
5. **USB に出てこないものはソフトからは何も見えない**(Tang Nano が見えない原因は充電専用ケーブルだった)→ skill に「疑う順番」
6. **Sipeed の BL702 は FT2232H のふりをする**(0403:6010)。シリアル番号 `FactoryAIOT Pro` は全個体で共通
7. **自前の IDCODE 表が間違っていた**(0x0100481B は GW1N(R)-9C)→ 外部ツールの DB を使う(層 1)。自前の表を持つ危うさの実例
8. **MCP クライアントは中継を最小限の環境変数で起動する**(`TMPDIR` がない)→ コアと中継が合わせる場所は環境変数に頼らない
9. **`serial.listen arg=9600` を 9600 秒と読んでいた** → 操作の引数に型と範囲を付けた
10. **Tang Nano のファブリック UART の無音は、元のビットストリームが何も出していなかったため**(テスト用ビットストリームで `hb` とバナーが出た)
11. **`panic` は `abort()` とバックトレースを出し、ROM のリセット理由は `RTC_SW_CPU_RST`**(Guru Meditation の行は出ない)。
    → ログの書式を表で持つと漏れる実例。解釈はエージェントの仕事(層 4)、注意すべき行の形は記憶へ

   - 承認の待ち時間(95 秒)が人が押す前に切れた。エージェントは承認番号を付けて呼び直せば続く(ふだんの流れ)
   - この開発のセッション(Claude Code)が、自分の依頼の承認ボタンを押すことは、自動モードの安全判定で止められた(正しい)。押したのは人

29. **レビュー 7 の直しが、実機の ESP32-S3 を 1 回リセットした**(2026-11-03、安全な操作だけの確認のつもりで、偵察と見張りとログの読み出しを
   製品の経路で動かした)。「記憶を当てはめてから偵察する」(レビュー 7 の 6)にしたことで、この口の「開いても安全」(人が確認済み)が偵察でも
   効き、偵察が初めてこの口を聞いた。ところが偵察は、口ごとの開き方(この口は DTR/RTS をそのままにして開けば安全、という同梱データ)を
   使わず、いつも DTR/RTS を落として開いていた。その開き方がまさにこのチップのリセットの仕方で、ログに `rst:0x15 (USB_UART_CHIP_RESET)`。
   前は記憶が偵察の後だったので、偵察はこの口を聞かず、表に出なかった。偵察も口の開き方で開くよう直し、テストを足し(古い作りでは落ちる)、
   実機で偵察がこの口を聞いても起動からの時間が続いていることを確かめた。教訓:安全の判定が「どう開くか」を前提にしているなら、開く経路は
   すべてその開き方を使うこと。判定を前に動かす直しは、それまで通らなかった経路を通すことになる

#### R3 の詳細:承認は人の経路からだけ

参考:**ssh-add -c + ssh-askpass**、**gpg-agent + pinentry**(確認は頼んだ側が操作できない別の経路で人に求める)。

- エージェントの経路(MCP の中継)はツールを呼ぶだけで、承認する手段がない。制御の経路は、コアを子プロセスとして起動した拡張だけが持つ
- 承認の状態はコアのメモリだけ。記録(監査ログ)はファイルに追記するが、書き換えても承認にはならない

**脅威モデル**:守る相手は、エージェントの **間違いと行き過ぎ**(勝手に承認する、ファイルを書き換える、ポートを直接開く)。
同じ利用者の権限で意図的に攻撃してくるプログラムは対象外。DANGEROUS な操作には、将来 OS の確認(Touch ID など)を挟む余地を残す。

**残る穴**:選んでいない機器は OS の排他がかかっていないので、エージェントがシェルから直接開けてしまう(instructions / skill の指示だけ)。
エージェントが自分で `benchscout core` を起動して制御の経路に入力を流し込むのは意図的な回避なので対象外(Claude Code 向けの設定では
`benchscout` を Bash から呼ぶことを deny にしておく)。

#### R8 の詳細:範囲と期限付きの許可

- **DISRUPTIVE な操作に限り**、(操作, 口) に対して「このセッションの間」または「N 分間」の許可を出せる
- **DANGEROUS な操作は**、(操作, 口, 引数) に紐付いた1回限り
- 範囲付きの許可も、出せるのは人だけ。選択から外れた機器、セッションの終了、期限切れで消える

### 5回目(2026-11-02):設計思想の根幹から見直し(「FPGA は openFPGALoader 決め打ちでは?」)

design.md §0〜§5、§17 を読み直し、原則ごとに実装を突き合わせた。

**沿っていたこと**:役割分担(benchscout に LLM 機能なし。正体の特定とログの解釈はエージェント)、入口は MCP だけ、承認は人の経路だけ
(テストで確認)、慎重な既定値と「同梱データを消しても安全側にしか倒れない」、記憶(自動で書き、安全を緩めるものだけ人)、受信箱、
自律の輪(見張る → 気づく → 起こす → 調べる → 残す)。コードに機器の名前はない(テストで見張っている)。

**ずれていたこと**:

| | 指摘 | 結論 |
|---|---|---|
| V1 | 道具の選択が benchscout 側に固定されていた。FPGA の書き込みは openFPGALoader、ESP は esptool の定義しかなく、それらが対応しない部品では、エージェントが正しい道具を見つけても benchscout の門を通して使う道がなかった。「どの道具で扱うか」は知識(エージェントの仕事)なのに、同梱データ(benchscout の仕事)として持っていた | `bench_define_tool`(エージェントが提案、人が確認、作業フォルダの知識へ)。design.md §3、§5 に原則として書いた |
| V2 | データの無い USB 機器は一覧に出なかった(シリアルポートかデータがある機器だけ)。シリアルポートの無い書き込み器(USB-Blaster、Platform Cable)はエージェントにも見えず、V1 の提案もできなかった。原則 1「列挙し、生の手がかりを取る」と、§2「初めて見る機器は VID:PID と名乗りで十分」に反していた | ハブを除くすべてを手がかりとして見せる。データの無い機器は「ほかの USB 機器」として分け、受信箱では件数だけ出す |
| V3 | 探す外部ツールの名前の一覧がコードにあった(使う定義の無い openocd や probe-rs まで「入っていない」と出していた) | データ(道具の操作の定義と USB の `tools`)から引く |

**なぜそうなったか**:

1. **設計の穴**:§4 は「外部ツールの操作はデータで定義する。コードを変えずに足せる」、§5 は「調べものはエージェント」と書いていたが、
   知らない部品のために **誰が** 道具の定義を足すのかを決めていなかった。実装はその穴を「同梱データ」で埋めた
2. **目の前のベンチに合わせた**:ESP32-S3 と Tang Nano で必要になるたびに、その道具とその見え方を同梱で足し、「このベンチで動く」で
   確かめていた
3. **見張っていたのは安全の一般性だけ**:見たことのない機器のベンチのテストは「慎重になるか」「名前を付けないか」を確かめていたが、
   「そのうえで仕事ができるか」(見えるか、道具を持ち込めるか)は確かめていなかった。だからずれがテストに出なかった

**再発を防ぐ形**:「同梱データを消しても安全側にしか倒れない」の対として、「同梱の道具の定義を消しても、知らない書き込み器が見え、
エージェントが道具を持ち込み、人の確認のあと門を通して使える」をテストにした(`test_without_any_shipped_tools_the_agent_can_still_bring_one`)。

| 8 | **安全の門(broker)が、全部の操作の実装を `if action == …` の分岐で持っている。** 判定と、機器への操作が混ざっている。プロトコルを足すには門を書き換えることになる |
| 9 | 見張りがシリアル専用で、baud が 115200 の固定 |
| 10 | 偵察が、USB の機器の役割ごと(チップ自身の USB、多チャネル、プローブ、ブリッジ)に別のコードでグラフを組む |
| 11 | 機器を名乗らせる手順がプロトコルごとに偵察の中に直書き(SCPI の `*IDN?`、シリアルは聞く、JTAG は決め打ちの道具) |

**なぜこうなったか**
1. **設計書は層(Transport / Codec / コマンド、データで定義する道具、知識の層)を書いたが、コードの境界にしなかった。** プロトコル、偵察の手順、
   開けない理由、配線の関係といった概念に、コードの中の「ただ 1 つの置き場所」が無い。置き場所の無い概念は、新しい場合が来るたびに
   どこかの分岐として足される。重複は当然の結果
2. **目の前のベンチから下から作った。** ESP32、Tang Nano、模擬の測定器で動くように足し、あとから名前をデータへ移して「汎用」にした。
   名前をデータへ移しても、仕組みが汎用になるわけではない(レビュー 7 の言うとおり。基板のデータに FPGA 専用の役割が残っている)
3. **見張りのテストが語を見ていて、構造を見ていない。** 機器名・会社名がコードに無いことは確かめるが、「1 つの概念が 1 か所にある」
   「門が操作の名前で分岐しない」「OS の名前は OS の層にだけ」は誰も見ていない。道具の名前も重複もすり抜けた
4. **直し方。** 頼まれたこと・見つかったことを、その場で分岐や欄やカードを足して直し、テストが通れば次へ進んだ。レビューのたびに
   その結果が見つかり、また足した。今日のレビュー 7 の直しでも分岐が増えた。構造に戻って考えたのは、指摘されてから
5. 設計書が計画と現状を同じ本文に書いていて、設計とコードの隔たりが見えなかった

**目指す構造**(design.md §3 の決定に書く):概念ごとに置き場所を 1 つにし、中心(門、偵察、記憶)はその置き場所の「型」にだけ頼る。

| 概念 | 置き場所 | 中心から見えるもの |
|---|---|---|
| 口の振る舞い(開いたときの扱い、運ぶプロトコル、道具の届き方、開くのに要るもの) | 同梱データと記憶 | 口の属性だけ |
| プロトコル(送る中身をコマンドに分ける、既定の影響度、答えの区切り、名乗らせ方) | プロトコルごとに 1 モジュール(行のシェル、SCPI) | 「プロトコル」の型 |
| 操作(送る・聞く・見張る、データで定義する道具、偵察で使う道具) | 1 つの登録簿 | 名前と影響度と実行する関数 |
| コマンドの規則(影響度、値の制限) | 1 つの表(既定 < 記憶 < 人) | 判定の結果 |
| 配線(何が何の中にあるか) | グラフの関係(同梱も覚えたものも同じ形) | 依存の関係 |
| 注意すべき行 | 1 つの「行の規則」 | 警告 |
| 開けない理由 | 1 つの形(何の道具が、何が要り、どう直す) | 1 種類のカード |

そして **構造を見張るテスト** を置く:口の種類・プロトコル・操作の名前・道具の名前・OS の名前は、それぞれの置き場所(プロトコルの
モジュール、OS の層、データ)にしか現れてはいけない。門と偵察と記憶には現れない。語の見張りの代わりに、置き場所の見張り。

**直した結果(2026-11-03)**:

| | どうなったか |
|---|---|
| プロトコル | `protocols/`(base、lines、scpi)にだけある。門(policy、broker)は「プロトコル」の型だけを使い、SCPI もシリアルも名指ししない。送る入口は 1 つ(`serial.command` を `serial.send` にまとめた)、「この機器では今後も」もどのコマンドにも効く |
| 操作 | 各プロトコルが自分の操作(送る・聞く・見張る、問い合わせる・画面を保存する)を持ち、門は名前で探して呼ぶだけ。`_execute` の `if action ==` は無くなった |
| 偵察 | プロトコルの名乗らせ方(SCPI は `*IDN?`、行は聞く)と、データで定義した偵察用の道具(`tools.toml` の `probe`)で回る。openFPGALoader の `--detect` もその定義の 1 つ。組み込みの `jtag.scan` は外した。JTAG の答えから部品の種類を推測しない |
| 配線 | 同梱の基板データも、覚えた配線と同じ `inside` の関係で書く。FPGA 専用の役割と、それ用のコードは無い |
| 注意すべき行 | 同梱・利用者・覚えたものを、1 つの形の「行の規則」として、見張りでも偵察でも同じ関数で見る |
| 開けない理由 | `access`(何が要るか、どのインターフェース、どの道具)1 つの形。言葉はレポートの 1 か所 |
| 保存 | 作業フォルダへの書き出しは 1 つの口(`new_artifact`) |
| 見張りの baud | 覚えた速さ(構成の記憶 `{"baud": n}`)、なければ既定 |

**見張り**:`tests/test_structure.py` が、具体的な名前(プロトコル、操作、道具、OS、口の種類での分岐)の置き場所を見る。
コメントと説明文は除き、コードだけを見る。古い broker を戻すと、SCPI、操作の名前、道具の名前を行ごとに挙げて落ちる。
拡張(TypeScript)も、言葉のファイル(i18n.ts)のほかでは操作・プロトコル・道具の名前で判断しない

### 2026-11-15 LGPL のライブラリのソース(利用者が案 1 を選択)
