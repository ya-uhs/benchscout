## 0. 1分で読む要約

- **何か**:PC に刺さった FPGA / MCU / 測定器を開いた瞬間に偵察し、「どれを見ますか?」と聞き、選ばれた機器の
  観察・診断・実機操作を、利用者のエージェントと一緒に進める **VS Code 拡張**
- **思想**:中身は skills と MCP のまま。違うのは **向こうから動く** こと(proactive + situated)
- **頭脳は利用者のエージェント**(Copilot、Claude Code、OpenAI 互換 API / ローカル LLM)。**機器の正体を調べる、ログを読み解く、
  手順を考える** のはエージェントの仕事。検索やデータシートもエージェントが使う。benchscout は LLM 機能を持たず、埋め込みもしない
- **benchscout は組み込み開発のハーネス(段取り役)**:見張る → 気づく → **利用者のエージェントを起こす** → エージェントが調べる →
  残す、の輪を回す。人は **受信箱の選択肢に答えるだけ** で進められる(意図を書いて変えることもできる)。最初にどの機器を見るかも
  benchscout が提案する(§17)
- **benchscout の仕事は 4 つだけ**:
  1. **生の手がかりを取る**(USB の VID/PID と機器が名乗る名前、IDCODE、`*IDN?` の答え、ログ)。正体の表は持たない
  2. **安全の門番**。知らないものは慎重な既定値で扱い、状態を変える操作は人がパネルで承認する
  3. **記憶**。ベンチで分かったことを **確認なしで自動で** 溜める。安全を緩める記憶だけは人が確認する
  4. **画面**。受信箱(質問・確認・報告・知らせ・覚えたこと)をパネルに出す
- **不明は不明**:名前は「機器の出力そのものの引用」が付いて、benchscout がその引用を照合できたときだけ「特定済み」にする
- **入口は1つ**:利用者のエージェント + MCP。画面は VS Code 拡張。配布は .vsix(Marketplace には出さない)
- **コードには仕組みだけ**:世の中の機器を表に書いていく作り方はしない(§5)

## 1. 出発点:何を作りたいか

HW開発でAIを使うとき、これまでは skills や MCP を用意して、人間が「このツールを使って」「このskillでやって」と頼んでいた。
人間が指揮役(オーケストレーター)になるので、そこがボトルネックになる。

目指すのは Meta Muse や Grok Bot のような、**向こうから動く** スタイル。

- ツールを開くと、繋がっている機器を自分で探して、デバッグや調査を **提案してくる**
  - 例:「ESP32 と FPGA(JTAG)が刺さってますよ。どれを見ますか?」
  - 例:「このデバイスは UART で反応しますよ。コマンドはこれっぽい」
- 常時監視ではない(できてもいい)。**開いた瞬間に場を偵察して報告する** のが基本
- 熟練者が机に来て、ケーブルを見ただけで状況を言い当てるイメージ。**一度見た机のことは覚えている**

### 一番大事な結論

> **中身は skills と MCP のまま。違うのは、向こうから動いてくれること。**

技術の差ではなく、主導権がどちらにあるかの差。「HWの専門家として最初から生まれた自律エージェント」。

### Meta Muse / Grok Bot などから何を取り入れるか

調べた内容(2026-10 時点、§8 の出典)から、思想ごとに採否を決めた。

| 思想 | 出どころ | benchscout での形 | 採否 |
|---|---|---|---|
| 頼まれる前に提案する | Muse | 開いたときの偵察と最初の見立て、提案カード | 採用(中核) |
| 隔離されたゲートを通らないと外に届かない(Sentinel) | Muse | ブローカー + ポリシー。**LLM ではなく決定的なルール** で判定する | 採用 |
| 機微な操作の前に必ず確認する | Muse / Grok Bot | 状態を変える操作は、人がパネルで承認する | 採用 |
| 汎用の画面操作より型の決まった connector を使う | Grok Bot | 型付きの操作だけを渡し、生のポートは渡さない | 採用 |
| **記憶は自動で書く。人が見て消せる** | Muse / Claude Code / Windsurf / ChatGPT | ベンチの記憶を確認なしで溜め、パネルで見て直せる。安全を緩める記憶だけ人が確認(§6) | 採用(中核) |
| 変わりうる事実は、記憶より今の情報源で確かめる | Grok Bot / Claude Code | 記憶には日付と根拠を付け、安く確かめられるものは使う前に確かめる | 採用 |
| うまくいった手順を skill として保存する | Grok Bot | 手順やコマンドの使い方も記憶に溜める(§4、§6) | 採用 |
| 目標 → 計画 → 進捗、監査ログ | Muse | 承認と操作の記録、パネルのタイムライン | 採用(後段) |
| スケジュールやイベントで起動する(Routines) | Grok Bot | USB 挿抜やログのパターンで起きる | 保留(できてもいい) |
| 常駐し、専用の環境を持つ | Grok Bot / Muse | 前提にしない。開いている間だけ動く | 当面不採用 |
| 複数の Bot が仕事を引き継ぐ | Grok Bot | ― | 当面不採用 |

Grok Bot の弱点として指摘されている「モデルを選べない」「権限が粗い」「監査ログがない」は、benchscout は
最初から持つ(モデルは利用者のエージェントで選ぶ、操作単位の承認、承認と操作の記録)。ここが差別化点。

### 名前について

定着した一語の呼び名はない。近い用語:

- **Proactive agent**:頼まれる前に動く(Muse はこれ)
- **Situated agent**:環境に埋め込まれて知覚・行動する(ロボティクス由来)
- **Ambient agent**:常駐してイベントで動く。常時監視寄りなので少しずれる
- **Infrastructure-as-Prompts**:Octopus Protocol 論文の用語。最も近い先行研究

正確に言うなら「proactive + situated なドメイン特化エージェント」。

## 2. 振る舞いの原則(UX)

1. **開いたら偵察 → 最初の見立て → 提案。** 人間はプロンプトを書かなくていい
2. **流れ:偵察 → benchscout が「どれをどう見るか」を選択肢で聞く → 人が選ぶ(または自由に書く)→ benchscout がエージェントを起こす**
   - **一覧は LLM を待たずに即座に出す。** 中身は「生の手がかり」と「記憶から分かっていること」
     - 初めて見る機器:「USB 1a86:7523 "USB Serial"(`/dev/cu.usbserial-10`)。正体はまだ不明」で十分。調べるのはエージェント
     - 前に見た機器:「ESP32-S3(2026-10-31 に起動ログで特定)。前回は brownout を起こしていた」のように記憶から即座に出る
   - 記憶にある注意点(前回のクラッシュなど)がある機器を先頭に出す
   - **複数選択が基本**。MCU + オシロ + 電源のように、組み合わせで初めてデバッグになる
   - **選んだものがセッションの範囲**。選んだ機器はコアが確保(acquire)し、提案の対象にする。選ばれていない機器には触らない
   - 選択肢を選ぶと、benchscout がその内容を添えてエージェントを起こす(§17)。**LLM を使うのはここから**
3. **最初は読むだけ。** 状態を変える操作は承認制
4. **不明は不明。** 推測で名前を付けない(§3「名前の付け方」)
   - 特定済み:機器自身が名乗った(`*IDN?`、USB ディスクリプタ)、外部ツールが答えた(openFPGALoader の IDCODE DB、esptool)、
     エージェントが機器の出力を引用して特定し、benchscout がその引用を照合できた
   - 推定:エージェントの見立てだが、機器の出力の引用で照合できないもの。名前の欄には出さず「推定」として分けて出す
   - 不明なものには「分かった事実」と「次に試せること」を出す
   - パネルの機器カードはブローカーのデータ(根拠付き)をそのまま出す。LLM の文章は会話欄にだけ出る
5. **名前や記憶には必ず根拠と日付を添える。** 人から聞いたことは「user said」、前のセッションで分かったことは「learned(いつ、何から)」
6. **ソフトから見えないことは人間に聞く。** オシロのプローブがどのネットに当たっているか、どの電源がどのボードに給電しているか。
   聞いた答えは記憶に残し、次から聞かない
7. **ユーザーの言語で話す。** 型番、パス、コマンド、ログの引用は訳さない

### 測定器

- 偵察で一緒に見つける(USBTMC / LAN / シリアル経由の SCPI、`*IDN?` で確定)
- 偵察で送るのは `*IDN?`(規格が意味を決めた問い合わせ)だけ。電圧・電流・出力の状態を読む問い合わせは、何が起きるかが機器しだいなので一度確認する。人が「この機器では今後も許可」を選べば、以後は聞かずに読める(§12 2026-11-02)
- **プローブの接続先は分からないので、聞く**(答えは記憶へ)
- オシロのトリガ変更のような無害に見える操作も承認制。人間が手元で見ている画面を勝手に変えない

### 波形

自前の波形ビューワーは作らない(少なくとも当面)。「ここに保存したよ」で十分。

- 保存するのは **オシロの画面キャプチャ(PNG)** と **生データ(CSV)**。保存先は開いている作業フォルダの中(エージェントが読める場所)
- エージェントの価値は **数値で報告すること**(「3V3 が 2.71V まで 3.2ms 落ちた、閾値は 2.8V」)
- じっくり見たいときは PulseView やオシロ純正ソフトで開けばいい
- 取り方は `scpi.query` の `save`(png / csv / bin など)。どの命令で画面や波形が返るかは機器しだいなので、エージェントがその機器のプログラミングマニュアルから選ぶ。benchscout は IEEE 488.2 のブロックの頭を外して作業フォルダに保存するだけ

## 3. アーキテクチャ

### 役割分担

| | benchscout(決定論、コード) | 利用者のエージェント(LLM) |
|---|---|---|
| 機器 | 列挙し、**生の手がかり** を取る:VID/PID、機器が名乗る名前、シリアル番号、IDCODE(外部ツール経由)、`*IDN?`、ログ。USB はハブを除く **すべて** を見せる(データの無い機器は「ほかの USB 機器」として分けて) | **正体を特定する**:手がかりを検索し、データシートや既存 DB を引き、機器の出力を引用して `bench_identify` で登録する |
| 道具 | 人が確認した道具の操作を、安全の門を通して実行する(ポートの持ち主の切り替え、影響の伝播、承認、記録)。同梱の道具の定義は「最初から少し便利」にするだけ | **どの道具で扱うかを調べて決める**(ベンダーの文書。同梱の道具が対応しない部品や書き込み器も)。`bench_define_tool` で提案し、人が確認する |
| 安全 | 門番。知らないものは慎重な既定値。承認は人の経路だけ | 承認を頼む。理由(`why:`)を引用する |
| ログ | 取って保存するだけ。記憶にある「この機器の注意すべき行」だけは照合して先頭に出す | **読み解く**(クラッシュ、RTOS の種類、異常)。注意すべき行の形を記憶に書く |
| 記憶 | 保管する。自分の観察(開いてもリセットしなかった、など)を自動で書く | 分かったことを自動で書く(`bench_remember`) |
| 画面 | 一覧、承認、記憶の確認・修正・削除 | 会話(エージェント自身の会話欄) |

- **benchscout に LLM 機能を作らない。** 自前のエージェントループ、LLM プロバイダの抽象化、エージェントの埋め込み(SDK)は作らない
- エージェントとは **MCP だけ** でつながる。どのエージェントでも同じ道具と同じ安全が効く
- 認証と課金は利用者のエージェントのもの(Claude Agent SDK を埋め込んで配る形だと、Anthropic の方針で claude.ai ログインを提供できない。notes.md レビュー R1)
- **決まった処理は LLM を通さない** のは、**列挙・手がかりの取得・安全の判定・記憶の照合** に限る。正体の判定やログの解釈は含めない
  (2026-10-31 の改訂。それ以前はここを広く解釈し、正体の表やログのパターンを benchscout に作り込んでいた。§12)

### 名前の付け方(不明は不明を、表なしで守る)

1. **機器自身や外部ツールが答えたもの** はそのまま特定済み(`*IDN?`、USB ディスクリプタの製品名、openFPGALoader の IDCODE DB、esptool の chip_id)
2. **エージェントが特定するとき** は `bench_identify(target, name, quote)` を使い、根拠として **機器の出力そのもの** を引用する。
   benchscout は、その引用が保存済みの出力(listen / send の記録、`*IDN?` の答え、ツールの出力)に **一字一句含まれるか** を照合する
   - 照合できた:特定済み。根拠は「agent-read: <引用>(<日時> の出力)」。名前の判断はエージェント、根拠の実在は benchscout が保証する
   - 照合できない:推定。名前の欄には出さず、パネルでは「推定」として分けて出す
3. 人が教えた名前は「user said」として特定済みにしてよい(根拠の種類で区別して表示する)
4. どの名前も記憶に残る(§6)。次に開いたときは LLM なしで出る

例:ESP32 のネイティブ USB の先は、USB ディスクリプタだけでは「ESP32 のどれか」まで。`reboot` 後の出力に
`ESP-ROM:esp32s3-20210327` があれば、エージェントがその行を引用して `ESP32-S3` と登録し、benchscout が引用を照合して特定済みにする。

### 安全の既定値(慎重に倒す)

- **知らないものは慎重に扱う。** 知らないシリアルポートを開くのは DISRUPTIVE(承認)、知らない操作は DANGEROUS
- **緩めるのは、観察と人の確認があるときだけ。** 例:「このポートは開いてもリセットしない」は、benchscout が実際に確かめた観察を
  記憶に書き、人がパネルで確認したら、次からそのポートの listen を SAFE にする(§6)
- **同梱のデータを全部消しても、安全側にしか倒れない** ことを作りの条件にする(同梱データは「最初から少し便利」にするだけ)
- **その対になる条件:同梱の道具の定義を全部消しても、できることは減らない。** エージェントが道具を提案し、人が確認すれば同じことが
  できる。同梱にしかない入口(「FPGA なら openFPGALoader」)を作らない(`test_without_any_shipped_tools_the_agent_can_still_bring_one`)
- 状態を変える操作を厳しくする知識は、機器名の表ではなく操作の種類の規則として持つ(§5 の層 2)
- **「危ないものの一覧」で格上げする作りにしない。** 一覧は完全にならず、漏れたものが弱く扱われる。既定を慎重にして、規格などで意味が決まっているものだけを緩める(例:SCPI は規格の状態・名前の問い合わせだけが SAFE、ほかの命令は毎回確認。§12 2026-11-02)

### プロセスと経路

```
VS Code
├── 利用者のエージェント(Copilot / Claude Code / Cline …)
│       │ MCP (stdio)
│       ▼
│   benchscout mcp(中継だけ。ブローカーを持たない)
│       │ エージェントの経路(ソケット / 名前付きパイプ):ツールを呼ぶだけ。承認の手段はない
│       ▼
├── benchscout 拡張(TypeScript)── 制御の経路(子プロセスの stdin/stdout)──► benchscout-core(Python)
│     パネル:機器、承認、記憶、タイムライン                             ブローカー、ポリシー、偵察、記憶、プロトコル層
│                                                                          │
│                                                                          ▼
│                                                                 実機 / 外部ツール
```

- **コアは拡張の子プロセス。** 制御の経路はその stdin/stdout そのもの。鍵やトークンは要らず、ファイルにも環境変数にも何も置かない。
  拡張(=そのウィンドウ)が閉じればコアも終わり、ポートを手放す
- **エージェントの経路はツールしか持たない。** `benchscout mcp` はエージェントが起動する中継で、コアのソケットにつなぐだけ
- **機器の確保はウィンドウをまたいで排他。** ウィンドウごとにコアができるので、機器ごとのロック(labgrid の acquire と同じ考え)で守る
- **確保したポートは OS のレベルで排他にする**(POSIX は `TIOCEXCL`、Windows の COM は元から排他)。エージェントがシェルから
  同じポートを開こうとしても失敗する。これが「ポートを直接触らせない」の実際の強制
- 開発とデバッグでは、`benchscout core` を起動した端末が操作盤の代わりになる(人が読める表示)

### レイヤー

```
L4  操作盤       VS Code 拡張のパネル(機器、承認、記憶、タイムライン)。コアのイベントを表示し、人の操作を制御の経路で送る
L3  エージェントの口 MCP(中継 → エージェントの経路)、MCP の instructions / prompts、skill
L2  ブローカー     ポートの持ち主、ポリシー、承認、セッション範囲、機器のロック、記憶、成果物フォルダ
L1  アクセス       Transport / Codec / コマンド(§4)、外部ツールの操作(データで定義)
L0  探索         USB 列挙、シリアルポート一覧、VISA 一覧、mDNS。何も開かない
```

(以前の「L1b 識別」は無くした。正体の特定はエージェント、benchscout は手がかりの取得と引用の照合だけ)

### MCP ツール

| ツール | 中身 |
|---|---|
| `bench_scan` | 一覧(手がかり、記憶、選択中の機器、提案、データの無い USB 機器) |
| `bench_inventory_json` | グラフ全体の JSON |
| `bench_impact` | 操作が何を乱すか、その理由 |
| `bench_do` | 操作の実行(承認が要れば人の判断を待つ)。機器のコマンドは記憶したものを `serial.command` で |
| `bench_log` | 見張っているポートのログ |
| `bench_identify` | 機器の出力を引用して名前を登録する(引用を照合) |
| `bench_remember` / `bench_recall` | 記憶を書く・引く(確認なし。安全を緩めるものは人の確認待ちになる) |
| `bench_define_tool` | 同梱していない道具の操作を提案する(人が受信箱で確認して加わる、§4) |
| `ask_user` / `request_devices` | 人への質問、機器の追加の依頼(選ぶのは人) |

- コマンドごとにツールを生やさない(エージェントが変わっても同じに見え、ツール数も増えない)
- 承認待ちの呼び出しは、人がパネルで決めるまで待つ(期限付き)。人が承認したことと待った秒数を結果に含める
- 振る舞いは skill で配り、守ってほしい最低限(承認を自分で出さない、`why:` を引用する、名前には引用を付ける)は MCP の instructions にも書く

### データモデル:スタックではなくグラフ

USB-UART、FT2232H(JTAG+UART)、ESP32-S3 内蔵 USB(シリアル+JTAG)、ST-Link(SWD+VCP)のように、実際の繋がりはプロトコルのスタックに分けられない。

```
物理デバイス(抜き差しの単位) ──持つ──> 口(開く・占有の単位) ──プロトコル──> 相手(関心と影響の単位)
```

- プロトコル(UART / JTAG / SCPI)はノードではなく **線のラベル**
- 相手は `hosted_on` を持てる(例:FPGA の中の UART は、FPGA を書き換えると落ちる)。この繋がりも記憶から足せる
- 分からない線は分からないまま持てる(CH340 の先は「?」)
- 一覧は「ポート単位」ではなく「ボード単位」で見せる
- 参考:**labgrid**(Resource / Driver / Target / Strategy、リソースのロック)

### ポリシー:読む/書くではなく、状態を変えるかで分ける

| 分類 | 例 | 扱い |
|---|---|---|
| SAFE | USB 列挙、`*IDN?` など規格の状態・名前の問い合わせ、JTAG IDCODE 読み取り、**開いても何も起きないと確認済みのポートを聞く**、人が「今後も許可」した測定器の命令 | 自動 |
| DISRUPTIVE | 知らないポートを開く、esptool(読むだけでもリセットが入る)、JTAG で CPU を止める、測定器への規格外の問い合わせや命令(許可はその命令だけに効く)、シリアルへの送信 | 承認 |
| DANGEROUS | フラッシュ書き込み、FPGA のコンフィグ、電源出力の変更、知らない操作 | 承認+警告 |

- 影響はグラフをたどって判定する(操作 → 乱す相手 → その上で動く相手 → それらに繋がる口すべて)
- 提案には必ずポリシーの理由(`why:`)を付け、エージェントはそれを引用する
- 承認は人の経路からだけ出せる。DANGEROUS は (操作, 口, 引数) に紐付き1回限り、DISRUPTIVE は (操作, 口) に範囲と期限付きでも出せる(notes.md レビュー R3、R8)
- 影響度が宣言されていない**操作**(外部ツールの定義など)は DANGEROUS。機器に送る**文字**(シリアルのコマンド、SCPI)で、規格も記憶も
  影響度を決めていないものは DISRUPTIVE(毎回聞く。許可は人が見たコマンドの語・ヘッダだけに効く)。覚えた影響度は、どの入口
  (`serial.command`、生の `serial.send`)から送っても効く(2026-11-03)
- **実行時の約束**(2026-11-03、notes.md レビュー 7):
  - 機器のポートを開く・開き直すのは、いつもブローカーが今の状態(選ばれているか、同じ個体か、今開いて安全か)で決める。見張りも勝手に開き直さない
  - 承認は、解決した中身(実際に送る文字、走らせる引数、定義)に結びつく。承認の後で定義が変わったら、その承認では走らない
  - 1 つの操作の影響度は、その全段階(開く、設定を変える、送る中身、道具)の強い方
  - 「緩める」は、既定値とではなく、今効いている一番強い規則と比べる。緩める記憶は、シリアル番号で一意に見分けられる個体にだけ効く
  - 見分けられない個体どうし(同じ型でシリアル番号が無い・共通)を、推測で結びつけない
  - 偵察は、記憶を当てはめてから機器と通信する

## 4. 機器とのやりとり:Transport / Codec / コマンド、外部ツールの操作

```
コマンド      名前・引数の型・影響度・応答の読み方                 ← 記憶(エージェントが覚える)/ 利用者のファイル
     │         例: status=safe, led {idx}=disruptive, reboot=dangerous
Codec         1回のやりとりの区切り方(汎用、パラメータで調整)
     │         line-shell(プロンプト正規表現、改行、エコー除去)/ scpi / at / binary(SLIP、COBS、長さ付き)
Transport     バイトを運ぶだけ。開く・専有・多重化はブローカー
               serial(baud など)/ tcp / visa / usb
―― 別系統 ――
外部ツールの操作  esptool / openocd / openFPGALoader など。データで定義する(下)。自分でポートを開くので、ブローカーが持ち主を切り替える
```

### 機器のコマンド

- **コマンドは主に記憶として溜まる。** エージェントが `help` の出力やファームのソースからコマンドを読み取り、`bench_remember` で書く。
  利用者が自分で書いたファイルも同じ形式で読む。**同梱はしない**(機器ごとに違うので、表にしても終わらない)
- **影響度を SAFE にするのは安全を緩めることなので、人がパネルで確認する。** 確認されるまでは送信と同じ DISRUPTIVE
- 生のバイト送信(`serial.send`)は常に承認制
- baud や改行コードなどの通信パラメータは記憶や設定に置く。コードに固定しない
- line-shell の Codec は「応答」と「勝手に出る行」を分ける(MCU のシェルはログを流しながら応答する。notes.md レビュー R7)
- 実装(2026-11-01):記憶の `command`(data `{command, effect, eol}`、対象は 1 つのシリアルポート)と操作 `serial.command {name}`。
  覚えていない名前は断り、覚えているものの一覧を返す。`effect` が safe のものは人が確認するまで `serial.send` と同じく承認制。
  disruptive / dangerous はそのまま記録して、その強さで承認を求める。シリアル番号が共通の機器では safe を緩めない。
- 実装(2026-11-03、line-shell の Codec):送った行のエコーを外し、`until`(答えを終える行の正規表現:プロンプト、`^(ok|err)`、AT なら
  `^(OK|ERROR)$`)が来たらそこで読むのをやめる。見張り中なら、送る前に機器が自分から出していた行と同じ形の行(数字は無視)を
  「勝手に出た行」として分けて返す(前のコマンドへの応答は比べる元に入れない)。推測なので何も捨てず、全文はファイルに残す。
  どの行で終わるかは機器ごとなので、エージェントが出力から読み取り、コマンドの記憶(data の `until`)に書く。バイナリの枠(SLIP、
  COBS)はまだ

### 外部ツールの操作(データで定義)

書き込み(FPGA の SRAM、フラッシュ)や JTAG 操作は、外部ツールの呼び出しとしてデータで定義する。コードを変えずに足せる。

```toml
[[tool]]                                   # packs/bench/data/tools.toml、利用者・作業フォルダの knowledge/*.toml も同じ形
name = "fpga.program"
effect = "dangerous"
reason = "loads a bitstream into the FPGA's SRAM: everything in the fabric restarts"
argv = ["openFPGALoader", "{port.select*}", "{bitstream}"]   # {port.select*}:この道具がこの口に届く方法(usb.toml の tools)
port_kinds = ["jtag"]
releases_device = true                     # 実行中は機器を手放し、見張りを止めて後で戻す
args.bitstream = { type = "file", required = true, ext = [".fs", ".bit"] }
```

同梱の定義は「最初から少し便利」にするだけで、同梱にしか無い入口は作らない。同梱していない道具(ベンダー公式のツールなど)は、
エージェントが文書から見つけて `bench_define_tool` で提案し、人が受信箱で実際に走る命令を見て確認すると、作業フォルダの知識
(`agent-tools.toml`)に入ってほかの操作と同じ規則で使える(§3 役割分担、§12 2026-11-02)

- シェルを通さず引数の配列で実行する。引数には型を付け、ファイルなら存在と拡張子を確かめる
- ツールの相性も同じ場所に書く(例:ESP32-S3 の USB-Serial/JTAG には esptool v5 以上。notes.md「実機で学んだこと」)
- 影響の伝播はグラフで計算される(FPGA を書くと中の UART も止まる)

## 5. 知識の持ち方:コードには仕組みだけ

原則:**コードには仕組みだけ。** 世の中の機器を表に書き足していく作り方はしない。機器もログの形も無限にあり、終わらない。
調べものはエージェントの得意分野(検索、データシート)なので、そちらに任せる。

| 層 | 何を | どこに | 例 |
|---|---|---|---|
| 1. 機器と外部ツールに聞く | 名前、型番 | 機器自身・外部ツール | USB ディスクリプタ、`*IDN?`、openFPGALoader の IDCODE DB、esptool |
| 2. 安全の規則(同梱、最小) | 操作の種類ごとの安全の規則だけ。**機器の名前の表は持たない** | 同梱データ(利用者・作業フォルダで上書き可) | 規格が意味を決めていない SCPI の命令は毎回確認、知らないポートは開くと承認、の既定値 |
| 3. 記憶(自動で溜まる) | このベンチ・この機器で分かったこと | 記憶ファイル(§6) | 「この CH340 の先は STM32、`status` コマンドがある」「このポートは開いてもリセットしない(人が確認済み)」 |
| 4. エージェント | 正体の特定、ログの解釈、手順 | 利用者のエージェント(検索・データシート) | 「この VID/PID は WCH の CH340」「このログはクラッシュ」 |

- **同梱データを全部消しても安全側にしか倒れない** こと(§3)。同梱は「最初から少し便利」にするだけ
- 層 2 に入れてよいかの基準:**なければ安全を誤るもので、名前を付けないもの**。入れてよいのは次だけ(2026-11-01 の決定、11-03 に本文を合わせた):
  USB インターフェースの、開いたときの扱い・運ぶもの・道具の届き方/基板のチャネルの配線(FPGA を書くと中の UART も止まる、と
  影響を伝えるため。**配線は安全のための仮定として言い、基板や部品の名前は出さない**)/SDK をまたぐ汎用のクラッシュの印/外部ツールの操作。
  機器や部品の名前、型番、ログの解釈は入れない(3 か 4)
- **どの部品をどの道具で扱うかは知識(層 4、確認後は層 3)。** 同梱の道具の操作(esptool、openFPGALoader)は便利のための既定で、
  それしか道がない作りにしない。足りないものはエージェントがベンダーの文書から見つけて提案し、人が確認して作業フォルダの知識に入る(§4)
- 「不明は不明」は層をまたいで守る(§3「名前の付け方」)

## 6. 記憶

Muse、Claude Code の自動メモリ、Windsurf、ChatGPT と同じく、**確認なしで自動で書く。人は後から見て直せる・消せる。**
違うのは 1 点だけ:**安全を緩める記憶は人の確認が要る**(承認を省くことにつながるため)。

### 何を覚えるか

| 種類 | 例 | 書く人 | 確認 |
|---|---|---|---|
| 正体 | 「ESP32-S3」(引用:`ESP-ROM:esp32s3-20210327`) | エージェント(`bench_identify`) | 不要(引用を照合) |
| 観察 | 「開いてもリセットしなかった(2 回)」「この UART は 115200 で `hb` を出す」 | benchscout が自動 | 不要 |
| 構成 | 「この UART は FPGA の中」「CH1 のプローブは 3V3」 | エージェント / 人の答え | 不要(影響を広げる・事実を足すだけ) |
| 解釈 | 「`abort() was called` が出たらクラッシュ」(この機器で注意すべき行の形) | エージェント | 不要 |
| コマンド | 「`status` で状態が出る」「`reboot` で再起動」 | エージェント | 影響度を SAFE にするときだけ要る |
| 安全を緩める | 「このポートは開いてもリセットしない → listen を SAFE に」 | benchscout の観察を元に提案 | **人の確認が要る** |

### どこに、どう持つか

- **機器ごと**:利用者全体の場所に置く(機器は作業フォルダをまたいで使うため)。鍵は VID:PID:シリアル番号
  - 全個体で同じシリアル番号の機器(Tang Nano の `FactoryAIOT Pro` など)は、別の個体の記憶かもしれないと明示し、安全を緩める記憶は使わない
- **作業フォルダごと**:このプロジェクトの配線やプローブの接続先(`.benchscout/memory/`)
- 人が読めて直せる形式にする(1 機器 1 ファイル)。パネルで一覧・修正・削除できる
- 各項目に **日付、根拠、誰が書いたか** を付ける

### どう使うか

- 偵察のたびに記憶を重ねて一覧を作る(LLM なしで、前に分かったことが即座に出る)
- **古くなりうる前提で使う。** 安く確かめられるもの(listen で `hb` が出るか)は、使う前に確かめる。食い違ったら新しい観察を優先し、古い項目は履歴として残す
  - 実装(2026-11-03):「開いても安全」として開いたポートが 3 秒以内に消えたら(開いたことでリセットか再接続が起きた)、安全を緩めていた
    記憶を「食い違い」(contradicted)にして履歴に残し、「開く前に確認する」という厳しい側の記憶をすぐ効かせる。人は受信箱で知り、消せば戻る
- エージェントには一覧と一緒に渡す(`bench_scan` の結果、`bench_recall`)

## 7. 範囲と拡張

- **範囲**:ベンチの観察・診断・実機操作(ログを聞く、コマンドを送る、IDCODE を読む、測定器を読む・設定する、承認付きでリセット)
- **書き込みも範囲に入れる**:FPGA の SRAM 書き込みとフラッシュ書き込みを、DANGEROUS の 1 回の操作として持つ(§4 の外部ツールの操作)。
  benchscout にしか出せない価値があるため:ポートの持ち主の切り替え(ログを止める → 手放す → 書く → 開き直す)、影響を先に示す、
  承認と記録、ツールの相性の知識
- **範囲外**:コード編集・ビルドを中心にしたワークフロー。利用者のエージェントや既存の拡張(ESP-IDF、PlatformIO)の仕事
- **開発ツール側へ広げやすくする構造**:中核はドメインを知らず、ドメインは pack として差し込む

```
Core(ドメイン非依存)
  ブローカー(ポリシー・承認・リース・ロック)、グラフ、記憶、監査ログ、MCP の口、制御の経路

Pack: bench   ← 今はこれだけ
  probes、外部ツールの操作(データ)、安全の規則(データ)、instructions / prompts / skill

Pack: dev     ← 将来
  ビルドなど。ソース → イメージ → ターゲットのノード
```

## 8. 画面(VS Code 拡張のパネル):受信箱

人に向けて出てくるものを、1 か所にカードで並べる(LangChain の Agent Inbox の型に、報告と覚えたことを足したもの)。
人は基本的にボタンを押すだけで進められ、どのカードにも「別のこと…」(自由入力)がある。上部には常に自由入力欄。

| カード | 何のためか | 出すのは | 答えないと |
|---|---|---|---|
| 質問 | 方向を決める(どれを見るか、どう進めるか) | benchscout(最初の選択)、エージェント(途中) | 待つ |
| 確認 | 状態を変える操作の承認、エージェントの他の道具(シェル、編集)の許可 | benchscout / エージェント | その操作だけ止まる |
| 報告 | 調査の結果と次の選択肢 | エージェント | 次の選択を待つ |
| 知らせ | 出来事を伝えるだけ(新しい機器など) | benchscout | 何も起きない |
| 覚えたこと | 記憶に書いた内容。安全を緩めるものだけ確認を求める | benchscout / エージェント | 普通の記憶は有効、安全を緩めるものは効かない |

- 1 つの調査 = エージェントとの 1 つのセッション。「途中経過を見る」でエージェントの考えやツールの呼び出しを流れる順に見られる
- 確認待ちは VS Code の通知とステータスバーにも出す
- 覚えていることは、機器の一覧の下に機器ごとに並ぶ(畳んだ状態から開く)。忘れる、確認待ちを認める・断る、記憶のファイル(読める TOML)を開いて直す
- 自律度(提案だけ / 自動で調べる)はパネルの上のボタンで切り替える(設定 `benchscout.autonomy` と同じもの、§17)

| 2026-11-03 | **実行時の約束を決めた**(§3:開くのはブローカー、承認は解決した中身に、影響度は全段階の強い方、緩めるは今の一番強い規則と比べ、緩める記憶は一意に見分けられる個体だけ、見分けられない個体を結びつけない、偵察は記憶の後)。外部のレビューで、ファイルやデータを分けただけで実行時の約束が無く、承認と違う中身が送られる・危険と覚えたコマンドを迂回できる・別の個体を操作しうる、が見つかった(notes.md レビュー 7) | 見つかった所だけ直す:同じ形の穴が別の入口に残る |
| 2026-11-03 | **知らないコマンドの既定の影響度を分けて決めた。** 影響度の無い操作の定義は DANGEROUS、機器に送る文字で影響度が決まっていないものは DISRUPTIVE(許可は人が見たコマンドの語だけ)、覚えた影響度は入口によらず効く(§3) | 送る文字もすべて DANGEROUS:`help` や `version` まで毎回 1 回限りの確認になり、記憶で減らす前に使えない。生の送信の許可をポート単位のまま:人が見ていない文字まで送れる |
| 2026-11-03 | **同梱データの範囲を本文に合わせ、配線は名前を出さない仮定にした**(§5) | 配線も外す:FPGA の書き込みが中の UART を止めることを、初めての基板で知る手段が無くなる |
| 2026-11-03 | **信頼の境界を書いた。** エージェントの経路(MCP)からは安全を緩められない。作業フォルダのファイルはその人のもので、信頼したフォルダの知識はエージェントが書いたものも効く。エージェントのファイルの書き込みは、エージェント自身の許可(受信箱の確認に出る)を通る。人の許可なしにファイルを書けるモードで動かしたエージェントは、この保証の外 | エージェントが書いた知識ファイルを毎回人に確認させる:人が意図して書かせる使い方を妨げる(11-02 の決定) |

## 15. 技術スタックと配布

### 決めたこと

- **配布は .vsix**(Marketplace には出さない)。中に **Python のコアを PyInstaller で固めた単体バイナリ** を同梱する
- **拡張は TypeScript**(VS Code の拡張は Node の上で動くので、Node を同梱する必要はない)
- **コアは Python のまま**

### コアを Python のままにする理由

| 層 | 必要なもの | Python | TypeScript(拡張の中) | Rust |
|---|---|---|---|---|
| ハードウェア | シリアル、VISA、USB 列挙、esptool など | ◎ pyserial、pyvisa-py(純 Python、NI-VISA 不要)、esptool 自体が Python | △ serialport はネイティブモジュールで拡張に入れにくい。VISA は実用的なものがない | △ VISA は NI-VISA が必要 |
| MCP サーバー | エージェントの口 | ◎ 公式(使用中) | ◎ 公式 | ○ rmcp |
| 既存資産 | コアとテスト | ◎ そのまま | × 書き直し | × 書き直し |

### .vsix にする上での仕事

- **OS と CPU ごとに .vsix を作る**(`vsce package --target darwin-arm64` など)。PyInstaller はクロスビルドできないので CI で OS ごとに作る
- **署名と誤検知**:Gatekeeper / SmartScreen の効き方は実機で確かめる(S5)。PyInstaller の exe は誤検知されることがある
- **更新**:Marketplace を使わないので自動更新はない
- **外部ツール**は先に入れさせない。利用者が入れたもの(PATH)を先に使い、無ければ操作が初めて要るときに公式のリリースから、版と SHA-256 を固定して取る(esptool。v5 以上:notes.md 実機 12)。どの OS でもそのまま動く公式ビルドが無い openFPGALoader だけはコアと一緒に配る(§12 2026-11-02)。同梱していない道具(ベンダー公式のツール)はエージェントが提案し、人が確認して加える(§4)

### Python の中での選択

| 用途 | 選択 | 理由 |
|---|---|---|
| 版と環境 | Python 3.11+、uv、hatchling | `tomllib` が標準で使える |
| 固め方 | PyInstaller(第一候補)、Nuitka(比較用) | 起動時間とサイズが問題なら Nuitka を試す |
| 並行処理 | スレッド + asyncio(MCP) | pyserial などの同期 I/O はスレッドで包む |
| 制御の経路 | stdin/stdout の JSON 行 | 子プロセスのパイプなので、ネットワークもトークンも要らない |
| エージェントの経路 | Unix ドメインソケット / Windows の名前付きパイプ(`multiprocessing.connection`) | 利用者だけが読み書きできる |
| データ形式 | TOML | 標準の `tomllib` で読める |

### 見直す条件

- コアの起動時間、サイズ、誤検知が許容できない → ブローカーとポートの持ち主から Rust に移す(制御の経路がプロトコルなので差し替えられる)
- ロジアナなど高レートのデータで Python が遅い → その経路だけを Rust に出す

## 17. 駆動と受信箱(自律の輪)

### 輪

```
見張る    選んだ機器を持ち続け、ログを流し続ける
  ↓
気づく    決まった処理で出来事を拾う(クラッシュ、リセットの繰り返し、挿抜、記憶にある注意すべき行)
  ↓
起こす    出来事を添えて、利用者のエージェントを起こす(下)
  ↓
調べる    エージェントが benchscout の道具を使う。SAFE は自分で進め、それ以外は受信箱で人に聞く
  ↓
残す      分かったことを記憶と受信箱(報告)に書く
  ↓
待つ      次の変化まで
```

人の役割は 3 つだけ:**受信箱の選択肢に答える**(機器の選択を含む)、**状態を変える操作を承認する**、**ソフトから見えないことに答える**。
benchscout はこの輪を回すハーネス。頭脳(LLM)は利用者のエージェントから借りる。

### エージェントの起こし方(既存の仕組みだけを使う)

| エージェント | 起こし方 | 許可の求めの受け取り方 | benchscout の道具の渡し方 |
|---|---|---|---|
| Claude Code | `claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio`(手を加えていない本体のヘッドレスモード) | `control_request` / `can_use_tool`(ツール名、入力、説明、許可ルールの候補が付く) | `--mcp-config`(stdio の中継) |
| ACP のエージェント(Copilot CLI、Codex、Gemini CLI …) | 公式 SDK `@agentclientprotocol/sdk` で ACP クライアントになる(`initialize` → `session/new` → `session/prompt`) | `session/request_permission`(選択肢:今回だけ許可 / 常に許可 / 拒否) | エージェントの起動オプション(Copilot CLI は `--additional-mcp-config`。ACP の `session/new` で渡す stdio の MCP は受け付けない) |

2026-11-01 の試作で、両方とも、benchscout が起こす → エージェントが `bench_do` を使う → コアで承認待ち → 人が許可 → エージェントが
「人の承認を経て done、最初の行は …」と報告する、までを模擬データのベンチで確認した(Copilot CLI 1.0.105、Claude Code 2.1.316)。

- **起こせなかったら止まって知らせる。** 受信箱に「起こせませんでした」と理由と直し方を出す。別のエージェントや LLM に勝手に切り替えない
- **資格情報に触れない。** ログインは各エージェント自身の仕組みで利用者がする。benchscout はログイン画面を出さず、トークンを持たず、リクエストを仲介しない
- **Claude Code の規約**(2026-11-03 に読み直した公式の Legal and compliance):「製品の中で Claude Code を動かす」ことは、
  ① 本体に手を加えず、組み込みの認証方法(Claude のアカウント、利用者自身の API キー)を外したり制限したりしない、
  ② 利用者の使用料を払ったり仲介したりせず、各利用者が自分の資格情報で認証し、自分に請求される、を条件に認められている。
  第三者が Claude.ai のログインを提供すること、利用者の Free / Pro / Max / Ultra の資格情報で代わりにリクエストを流すこと、
  資格情報やセッションのトークンを集める・保存する・仲介することは認められない。一方「利用者が手を加えていない本体に自分の
  サブスクリプションでサインインすることは妨げない」とも明記されている。benchscout は利用者が入れてサインインした `claude` を
  そのまま `-p` で起動するだけで、資格情報にも環境にも触れないので、この条件の内側にある。残る条件は 3 つ:配る側が商用の利用規約
  (Commercial Terms)に同意すること、名前は「Claude Code を動かす」と文字で書くだけにし、Anthropic や Claude Code の名前・ロゴを
  自分の製品名やロゴに使わないこと、プランの使用量は「普通の個人の使い方」を前提にしているので、自動で起こす回数に上限を持つこと(下の自律度)

### 自律度

| 段階 | benchscout がすること |
|---|---|
| 提案だけ | 質問と知らせを出す。エージェントを起こすのは人がボタンを押したとき |
| 自動で調べる(既定) | 選んだ機器を見張り続け、機器が選ばれたときと、注意すべき出来事(クラッシュ、リセット)のときに、エージェントを起こして調べさせる |

- パネルの上のボタンで切り替える(設定 `benchscout.autonomy` に残り、次の窓でも同じ)

- 費用の上限を持つ(1 時間あたりのターン数など)。上限に来たら受信箱で知らせて止まる
- 自律で動いている間も、状態を変える操作は人の承認待ち。人がいない間は読むだけの調査を進め、承認待ちを溜める

### 承認の重なりの扱い

エージェント自身も道具を使う前に許可を求める(ACP の `session/request_permission`、Claude Code の `can_use_tool`)。

- **benchscout の道具**(`mcp__benchscout__*`、ACP では benchscout の MCP サーバーの道具)についての許可の求めは自動で許可する。
  門番は benchscout 自身で、ハードウェアの操作はコアの承認を通る
- **エージェントの他の道具**(シェル、ファイル編集、Web)についての許可の求めは、受信箱の「確認」に出す
