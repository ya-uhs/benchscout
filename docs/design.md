# benchscout 設計メモ

このプロジェクトの「なぜ」と「何を決めたか」をまとめたもの。コードを読んでも分からない前提と判断をここに残す。
**思想・方向性の正本はこのファイル。** README.md と CLAUDE.md はここの要約で、食い違ったらこちらが正しい。
方向性を変えたら、まずここ(特に §11 決定ログ)を直してから他を合わせる。

(2026-10 のチャットでの議論から起こした。最終更新 2026-10-31)

## 0. 1分で読む要約

- **何か**:PC に刺さった FPGA / MCU / 測定器を起動時に自分で偵察し、見立てを添えて「どれを見ますか?」と聞き、
  選ばれた機器の観察・診断・実機操作をエージェントが進めるホストアプリ(GUI。Tauri の単体バイナリで配布、§14)
- **思想**:中身は skills と MCP のまま。違うのは **向こうから動く** こと(proactive + situated)
- **頭脳は既存エージェント**:LLM の推論、ファイル操作、シェル、会話管理は Claude Code / GitHub Copilot に任せる。
  benchscout は LLM 機能を自前で作らず、**SDK で既存エージェントを内部に埋め込む**
- **benchscout が持つもの**:起動と偵察、機器の門番(ブローカー)、知識とプロトコル定義(データ)、提案と承認の UI
- **範囲**:ベンチの観察・診断・実機操作に絞る。ただし開発ツール側(コード編集・ビルド・書き込み)へ
  pack を足すだけで広げられる構造にしておく
- **ハードコードしない**:コードは仕組みだけ。知識・プロトコル・手順・設定はデータファイル

## 1. 出発点:何を作りたいか

HW開発でAIを使うとき、これまでは skills や MCP を用意して、人間が「このツールを使って」「このskillでやって」と頼んでいた。
人間が指揮役(オーケストレーター)になるので、そこがボトルネックになる。

目指すのは Meta Muse や Grok Bot のような、**向こうから動く** スタイル。

- ツールを開くと、繋がっている機器を自分で探して、デバッグや調査を **提案してくる**
  - 例:「ESP32 と Xilinx FPGA(JTAG)が刺さってますよ。どれを見ますか?」
  - 例:「このデバイスは UART で反応しますよ。コマンドはこれっぽい」
- 常時監視ではない(できてもいい)。**起動した瞬間に場を偵察して報告する** のが基本
- 熟練者が机に来て、ケーブルを見ただけで状況を言い当てるイメージ

### 一番大事な結論

> **中身は skills と MCP のまま。違うのは、向こうから動いてくれること。**

技術の差ではなく、主導権がどちらにあるかの差。「HWの専門家として最初から生まれた自律エージェント」。

### Meta Muse / Grok Bot から何を取り入れるか

調べた内容(2026-10 時点、§8 の出典)から、思想ごとに採否を決めた。

| 思想 | 出どころ | benchscout での形 | 採否 |
|---|---|---|---|
| 頼まれる前に提案する | Muse | 起動時の偵察と見立て、提案カード | 採用(中核) |
| 隔離されたゲートを通らないと外に届かない(Sentinel) | Muse | ブローカー + ポリシー。ただし **LLM ではなく決定的なルール** で判定する | 採用(既存) |
| 機微な操作の前に必ず確認する | Muse / Grok Bot | 状態を変える操作は承認制 | 採用(既存) |
| 汎用の画面操作より型の決まった connector を使う | Grok Bot | 型付きの action / コマンドだけを渡し、生のシェルやポートは渡さない | 採用(既存) |
| 目標 → 計画 → 進捗、やったこと・やることの監査ログ | Muse | 「調査」単位(目標・計画・根拠・実行した操作)と GUI のタイムライン | 採用(後段) |
| 記憶(一度言ったことを覚える、忘れさせられる) | Muse | ベンチの記憶(プローブの接続先、配線、過去の所見)。人の発言は根拠「user said」として区別する | 採用(後段) |
| うまくいった手順を skill として保存する | Grok Bot | コマンド辞書やプレイブックの下書きをエージェントが作り、人が承認したら追記 | 採用(後段) |
| スケジュールやイベントで起動する(Routines) | Grok Bot | USB 挿抜やログのパターンで起きる | 保留(できてもいい) |
| 常駐し、専用の環境を持つ | Grok Bot / Muse | 前提にしない。ただしセッション中にポートを持ち続けることは必要 | 当面不採用 |
| 複数の Bot が仕事を引き継ぐ | Grok Bot | ― | 当面不採用 |

Grok Bot の弱点として指摘されている「モデルを選べない」「権限が粗い」「監査ログがない」は、benchscout は
最初から持つ(バックエンド選択、操作単位の承認、承認と操作の記録)。ここが差別化点。

### 名前について

定着した一語の呼び名はない。近い用語:

- **Proactive agent**:頼まれる前に動く(Muse はこれ)
- **Situated agent**:環境に埋め込まれて知覚・行動する(ロボティクス由来)
- **Ambient agent**:常駐してイベントで動く。常時監視寄りなので少しずれる
- **Infrastructure-as-Prompts**:Octopus Protocol 論文の用語。最も近い先行研究

正確に言うなら「proactive + situated なドメイン特化エージェント」。

## 2. 振る舞いの原則(UX)

1. **起動したら偵察 → 報告 → 提案。** 人間はプロンプトを書かなくていい
2. **起動の流れ:偵察 → 見立て付きの一覧 → 「どれを見ますか?」(1つでも複数でも)**
   - ただの一覧ではなく見立てを添える。異常がある機器を先頭に出し、おすすめの組み合わせを初期選択にする
     - 例:「ESP32-S3 がリセットを繰り返しています(`rst:0xf BROWNOUT_RST`)。オシロ DS1054Z もあります。この2つで電源を見ますか?」
   - 入口は2つ。「このデバイスを使いたい」(入力欄から絞り込む)と「どれか分からない」(一覧から選ぶ)。同じ偵察結果を使う
   - **複数選択が基本**。MCU + オシロ + 電源のように、組み合わせで初めてデバッグになる
   - **選んだものがセッションの範囲**。ブローカーが専有するポート、聞き続けるログ、提案の対象はここで決まる。選ばれていない機器には触らない
3. **最初は読むだけ。** 状態を変える操作は承認制
4. **不明は不明。** 推測で名前を付けない。根拠付きの同定と推測を分ける
   - 根拠付き:`esptool` がチップ名を返した、IDCODE が一致した、`*IDN?` が答えた
   - 観察事実:CH340 がある、115200bps で `[I] sensor ok` が来る → 正体は「不明」とし、事実だけを並べる
   - 推測:「たぶん ESP8266」→ 出さない
   - 不明なものには「分かった事実」と「次に試せること」を出す
5. **名前を出すときは必ず根拠を添える。** 人から聞いたことは根拠の種類「user said」として、測った事実と区別する
6. **ソフトから見えないことは人間に聞く。** オシロのプローブがどのネットに当たっているか、どの電源がどのボードに給電しているか
7. **ユーザーの言語で話す。** 型番、パス、コマンド、ログの引用は訳さない

### 測定器

- 起動時の偵察で一緒に見つける(USBTMC / LAN / シリアル経由の SCPI、`*IDN?` で確定)
- 状態(電源の電圧・電流・出力ON)は読むだけで取れるので、最初から把握しておく
- **プローブの接続先は分からないので、聞く**
- オシロのトリガ変更のような無害に見える操作も承認制。人間が手元で見ている画面を勝手に変えない

### 波形

自前の波形ビューワーは作らない(少なくとも当面)。「ここに保存したよ」で十分。

- 保存するのは **オシロの画面キャプチャ(PNG)** と **生データ(CSV)**
- エージェントの価値は **数値で報告すること**(「3V3 が 2.71V まで 3.2ms 落ちた、閾値は 2.8V」)
- じっくり見たいときは PulseView やオシロ純正ソフトで開けばいい

## 3. アーキテクチャ

### 役割分担:頭脳とファイル操作は既存エージェント、benchscout はホスト

「頭脳はバックエンド」とは、**benchscout に LLM 機能を作らない** という意味。

- LLM の推論、ファイルの読み書き、シェル、会話とコンテキストの管理は、既存のエージェント(Claude Code、GitHub Copilot)を使う
- benchscout に自前のエージェントループや LLM プロバイダの抽象化は作らない
- 「偵察はこのツール、デバッグはバックエンドに引き継ぎ」という分け方は **しない**。最初からバックエンドのセッション1本で動かす

**呼び方:外から起動するのではなく、benchscout がホストになって SDK で内部に埋め込む。**

| 方式 | 中身 | 位置づけ |
|---|---|---|
| Claude Agent SDK(Python / TypeScript) | Claude Code と同じエンジンをライブラリとして埋め込む(Python 版は CLI 同梱)。ツールごとの許可コールバック、hooks、MCP、セッション再開 | 最初に実装する |
| GitHub Copilot SDK(2026-06 GA。Node/TS・Python・Go・.NET ほか) | Copilot CLI をサーバーモードで起動し JSON-RPC でつなぐ(Python 版は CLI 同梱)。権限ハンドラ、MCP、カスタムツール、ストリーミング | 2本目 |
| ACP(Agent Client Protocol) | エディタとエージェントの共通プロトコル。Copilot CLI はネイティブ(preview)、Claude Code はコミュニティのアダプタ | 将来。Codex など他のエージェントを載せる口 |
| CLI のヘッドレス実行(`claude -p` など) | 子プロセス | 使わない(制御が効かない) |

埋め込む理由:

1. **承認を強制できる。** ツール呼び出しの許可判定が benchscout のコードになるので、エージェントが
   `benchscout approve` をシェルで打つ、`/dev/cu.*` を直接開く、といった操作を確実に拒否できる(skill の「お願い」ではなくなる)
2. **GUI にエージェントの動きを流せる。** 発言、ツール呼び出し、承認待ちがイベントとして届く
3. **起動プロンプト、skill、MCP の設定をコードで渡せる。** 作業フォルダに設定ファイルを書かなくてよい

バックエンドの差は薄いアダプタ(L3)だけで吸収する。SDK は版が変わりやすいので、アダプタの外に SDK の型を漏らさない。
外から素の Claude Code で使う道(`benchscout setup` で `.mcp.json` と skill を置く)も残す。
認証と課金はバックエンドごとに違う(Copilot はサブスクの premium request か BYOK、Claude Agent SDK は要確認)。

**決まった処理は LLM を通さない。** USB 列挙や `*IDN?` は、ツールが先に済ませて結果を最初の文脈として渡す
(速い、毎回同じ結果、トークンを使わない)。

benchscout に残る価値は4つ:

1. **起動しただけで動き出す**(偵察し、決まった最初の文脈でセッションを始める)
2. **機器の門番(ブローカー)**:どのバックエンドでも同じ安全ポリシーが効く
3. **専門家としての振る舞いと知識**:skill(手順、方針)、知識データ、プロトコル定義
4. **提案と承認の UI**

### レイヤー

```
L4  UI (GUI)         一覧、ログ、会話、カード、承認ボタン。ブローカーとアダプタのイベントを表示するだけ
L3  バックエンドアダプタ  Claude Agent SDK / Copilot SDK / (ACP)。起動、最初の文脈、skill、MCP、ツール許可の判定
        ↓ MCP
L2  ブローカー        ポートの持ち主、ポリシー、承認待ちの列、セッション範囲、記憶、成果物フォルダ
L1b 識別            正体+根拠を返す(アクセス層をブローカー経由で借りる)
L1a アクセス          コマンド辞書 → Codec → Transport(§4)、外部ツールのアダプタ
L0  探索            USB 列挙、シリアルポート一覧、VISA 一覧、mDNS。何も開かない
```

境界の決め方:

- **承認はブローカーで行う**(UI でもエージェントでもない)。バックエンドを差し替えても安全は変わらない。
  L3 の許可判定は「ブローカーを迂回させない」ための二重の柵
- **人間への質問もブローカー経由**(`ask_user` のような MCP ツール)にすれば、UI はブローカーのイベントだけ見ればよい(未実装)
- **ポートはブローカーが持つ。** バックエンドに `/dev/cu.*` を直接触らせない
- **MCP = 何ができるか**(能力+ポリシー)、**skill = 専門家ならどうするか**(手順、勘所)、**偵察 = コード**(決定論的)
- **MCP ツールは汎用に保つ。** `bench_scan` / `bench_impact` / `bench_do` に加え、`bench_commands(target)`(使えるコマンドと影響度の一覧)と
  `bench_call(target, command, args)`。コマンドごとにツールを生やさない(バックエンドが変わっても同じに見え、ツール数も増えない)
- **通信路と外部ツールは別物。** esptool や openocd は自分でポートや USB を開くので、ブローカーが「持ち主の切り替え」をする
  (ログ配信を止める → 手放す → ツールを実行 → 開き直す)

### データモデル:スタックではなくグラフ

USB-UART、FT2232H(JTAG+UART)、ESP32-S3 内蔵 USB(シリアル+JTAG)、ST-Link(SWD+VCP)のように、実際の繋がりはプロトコルのスタックに分けられない。

```
物理デバイス(抜き差しの単位) ──持つ──> 口(開く・占有の単位) ──プロトコル──> 相手(関心と影響の単位)
```

- プロトコル(UART / JTAG / SCPI)はノードではなく **線のラベル**
- 相手は `hosted_on` を持てる(例:FPGA の中の UART は、FPGA を書き換えると落ちる)
- 分からない線は分からないまま持てる(CH340 の先は「?」)
- 一覧は「ポート単位」ではなく「ボード単位」で見せる
- 参考:**labgrid**(Resource / Driver / Target / Strategy、リソースのロック)

### ポリシー:読む/書くではなく、状態を変えるかで分ける

| 分類 | 例 | 扱い |
|---|---|---|
| SAFE | USB 列挙、流れているログを読む、`*IDN?`、電源の電流値を読む、JTAG IDCODE 読み取り | 自動 |
| DISRUPTIVE | esptool(読むだけでもリセットが入る)、JTAG で CPU を止める、オシロの設定変更、**リセットがかかりうるポートを開く** | 承認 |
| DANGEROUS | フラッシュ書き込み、電源出力の変更、FPGA のコンフィグ | 承認+警告 |

- 影響はグラフをたどって判定する(操作 → 乱す相手 → その上で動く相手 → それらに繋がる口すべて)
- 提案には必ずポリシーの理由(`why:`)を付け、エージェントはそれを引用する(推測させない)
- 承認は (操作, 口, 引数) に紐付き、1回限り
- ユーザー定義コマンドは影響度を宣言する。**宣言がないものは DANGEROUS 扱い**(今の「未知の操作」と同じ)

## 4. プロトコル層とユーザー定義コマンド

一般的なプロトコルは同梱するが、ユーザーが実装したコマンド(MCU 内蔵シェルなど)もある。
それを **設定ファイルだけで足せる** ようにする。難しいのはレイヤーの切り方で、次の3段に分ける。

```
コマンド辞書  名前・引数の型・影響度・応答の解析            ← ユーザー設定 / 同梱パック(データ)
     │         例: status=safe, led {idx}=disruptive, reboot=dangerous
Codec         1回のやりとりの区切り方(汎用、パラメータで調整)
     │         line-shell(プロンプト正規表現、改行、エコー除去)/ scpi / at / binary(SLIP、COBS、長さ付き)
Transport     バイトを運ぶだけ。開く・専有・多重化はブローカー
               serial(baud など)/ tcp / visa / usb
―― 別系統 ――
外部ツールアダプタ  esptool / openocd / openFPGALoader。自分でポートを開くので、ブローカーが持ち主を切り替える
```

- **ユーザーが足すのは基本的にコマンド辞書だけ。** Codec と Transport はパラメータで選ぶ。新しい Codec が要るときだけコードを書く
- **同梱プロトコルもユーザー定義と同じ形式のファイル**(SCPI 共通コマンド、AT、Zephyr shell、ESP-IDF console、U-Boot など)。
  コードに特別扱いを残さない
- **紐付けは根拠で決める。** 「この基板にこのシェルがある」は、USB の VID/PID・シリアル番号、起動バナーの正規表現、
  GUI での人の割り当て(根拠「user said」)のどれかで決める。確かめるためのコマンドの試し打ちは、未知の UART に
  バイトを書くことになるので承認制
- **生のバイト送信(`serial.send`)は常に承認制**
- baud や改行コードなどの通信パラメータは Transport/Codec の設定に置く。コードに固定しない
- 学習:エージェントが `help` の出力などからコマンド辞書の下書きを作り、人が承認したらファイルに追記する(Grok Bot の「手順を skill にする」に相当)

定義の例(形式は TOML 案。§12 で未決):

```toml
[protocol.myboard]
codec = "line-shell"
transport = { kind = "serial", baud = 115200 }
prompt = '^myboard> $'
line_ending = "\r\n"

[protocol.myboard.match]          # この根拠がそろったときだけ紐付ける
usb = ["1a86:7523"]
banner = 'MyBoard fw v\d+'

[[protocol.myboard.command]]
name = "status"
send = "status"
effect = "safe"
parse = { regex = 'vbat=(?P<vbat_mv>\d+)mV' }

[[protocol.myboard.command]]
name = "led"
send = "led {idx} {on}"
args = { idx = "int", on = "bool" }
effect = "disruptive"
```

置き場所は「同梱 → ユーザー全体 → 作業フォルダ」の順に重ね、後ろが優先(案)。

## 5. ハードコードしない

原則:**コードには仕組みだけ。知識・プロトコル・手順・設定はデータ。**
目標は、中核のコードに `serial` や `ESP32` のような特定の機器・プロトコル名が出てこない状態(テストで確認できる)。

今のコードで外に出すもの(2026-10-31 の棚卸し):

| 場所 | 中身 | 移す先 |
|---|---|---|
| `knowledge.py` | USB_IDS、IDCODES、LOG_SIGNATURES、基板の配線(lambda でのマッチ)、測定器の種類 | 知識データファイル。既存 DB(USB ID、openFPGALoader、udev ルール)を優先し、自前の表は補助 |
| `policy.py` の `ACTIONS`、`_ENERGIZING` | 操作ごとの影響度 | 各 action / コマンドが自分で宣言する |
| `broker._execute` | 操作ごとの if の連鎖 | Action レジストリ(名前、影響度、引数の型、実行) |
| `recon.run` | `port.kind` での分岐、`vid == 0x0403` の判定 | Probe のレジストリ |
| `recon.propose` | `"ESP32"` の文字列判定、`"3V3 rail"`、`":SINGle"` | 提案ルールのデータ、または skill / エージェントに任せる |
| 各所 | 115200 baud、listen 2 秒、`TOOLS`、`BACKENDS`、`LANGUAGE_NAMES` | 設定ファイル |

ただし抽象化のための抽象化はしない。2つ目の実例が出たときに仕組みにする。

## 6. 範囲と拡張:観察・診断・実機操作に絞る

- **今の範囲**:ベンチの観察・診断・実機操作(ログを聞く、IDCODE を読む、測定器を読む・設定する、承認付きでリセット・SRAM 書き込み)
- **範囲外**:コード編集・ビルド・フラッシュ書き込みを中心にしたワークフロー。benchscout はこれを主導する UI や action を作らない

## 9. 実機で学んだこと(コードに反映済み)

模擬データでは一つも出なかったものばかり。

1. **ネイティブ USB の ESP32 は、ポートを開いただけでリセットされうる**(macOS)。読んでいる最中にポートが消えて USB が再接続された。→ 開く操作を DISRUPTIVE に。消えたポートはクラッシュではなく事実として記録
2. **VISA の一覧にシリアルポート(`ASRL…`)も混ざる。** そこに `*IDN?` を送ると、未知の UART にバイトを書き込むことになる → ASRL は VISA 側で扱わない
3. **引数付き SCPI クエリ**(`MEAS:CURR? CH1`)を書き込み扱いしていた → コマンドのヘッダで判定
4. **Tang Nano 9K が認識されない原因はケーブル**(充電専用)。USB に出てこないものはソフトからは何も見えない → skill に「疑う順番」を追加
5. **Sipeed の BL702 は FT2232H のふりをする**(0403:6010)。シリアル番号 `FactoryAIOT Pro` は全個体で共通
6. **自前の IDCODE 表が間違っていた**(0x0100481B は GW1N(R)-9C)。→ openFPGALoader 自身のデータベースを優先し、根拠にどちらで判定したかを書く
7. **openFPGALoader を ESP32 の USB-JTAG に向けていた** → FTDI 互換の JTAG だけに限定
8. 費用:最初の報告は1回あたり約 0.16〜0.32 ドル(定価換算)。大半は Claude Code 本体の前提文脈の読み直し

## 10. 実機で見つかり、原因は分かったが未修正のもの

1. **`serial.listen` の `arg=9600` が 120 秒以上返らない。** `broker._execute` が `arg` を **秒数** として `float(arg)` している
   (9600 秒待っていた)。baud は `recon.listen_into` で 115200 に固定で、変える手段がない。
   → Action レジストリで引数に型を付け(秒と baud を分ける)、MCP の docstring にも書く
2. **`port="/dev/cu.usbmodem1101"` だと黙って失敗する。** `classify` が口を id(`serial:…`)でしか引かず `KeyError` になる。
   → パスからも引けるようにするか、期待する id を並べたエラーを返す
3. **Tang Nano のファブリック UART が既定のレートで無音。** 上の 1 のせいで baud を変えて試せず、baud か bitstream かは未切り分け
4. **承認をファイルの書き換えで偽造できる。** 承認の状態が作業フォルダの `.benchscout/approvals.json` にあり、エージェントが書ける(§15 R3)

## 14. 技術スタック

2026-10-31 に決めたこと:**exe などの単体バイナリで配布する。デスクトップの殻は Electron ではなく Tauri。**
コアを Python のままにするかは、この前提で検討し直した(下の「判断」)。

### 層ごとの比較

| 層 | 必要なもの | Python | TypeScript / Node | Rust |
|---|---|---|---|---|
| ハードウェア | シリアル、VISA、USB 列挙、esptool など | ◎ pyserial、pyvisa-py(純 Python、NI-VISA 不要)、esptool 自体が Python、pytest-embedded、labgrid | △ serialport はあるが、VISA は実用的なものがない | △ serialport はある。VISA は NI-VISA が必要 |
| エージェント SDK | Claude Agent SDK、Copilot SDK | ◎ 両方あり、どちらも CLI 同梱 | ◎ 両方あり(ただし Node の実行環境が要る) | △ Copilot のみ、Claude はなし |
| MCP サーバー | ブローカーの口 | ◎ 公式(使用中) | ◎ 公式 | ○ rmcp |
| 数値処理 | 波形を数値で報告する | ◎ numpy | △ | △ |
| GUI | 一覧、ログ、会話、承認 | △ 単体では弱い | ◎(画面) | ◎ Tauri(画面は Web) |
| 単体バイナリ | Win / Mac / Linux | △ PyInstaller などで固める。大きく、手間がある | △ Node ごと同梱(Electron 相当) | ◎ |
| 既存資産 | 約 1250 行 + テスト | ◎ そのまま | × 書き直し | × 書き直し |

### 判断

- **殻は Tauri(Rust)、画面は TS、コアは Python のまま。** コアは Tauri のサイドカー(同梱の別バイナリ)として PyInstaller で固める
- Tauri にしても、コアを Rust に書き直す理由は弱い。VISA が NI-VISA 頼みになり、Claude Agent SDK に Rust 版がなく、既存資産も捨てることになる
- TS コアは、SDK を動かすために Node を同梱することになり、Electron を避けた意味が薄れる
- 境界をイベントのプロトコルにしておけば、サイドカーの負担が大きくなったときに、コアの一部(ブローカーやポートの持ち主)を後から Rust に移せる

### 構成

```
benchscout.exe / .app / AppImage  (Tauri)
├── 殻(Rust、薄く保つ)  ウィンドウ、サイドカーの起動と監視、終了処理、自動更新
├── 画面(TypeScript + Vite、フレームワークは未決)
│       ↑↓ WebSocket(127.0.0.1 のみ、起動ごとのトークン必須。JSON のイベントとコマンド、スキーマは pydantic から JSON Schema で出す)
└── サイドカー:benchscout-core(Python を PyInstaller で固めたもの)
        ブローカー、ポリシー、偵察、プロトコル層、MCP の口、バックエンドアダプタ(SDK と同梱の CLI)
        ↓
    実機 / 外部ツール(openFPGALoader、openocd などは当面 PATH から探す。esptool は Python なので同梱できる)
```

- **画面とコアは別プロセス。** 承認はブローカーにしかないので、画面からもすり抜けられない(§3)
- **殻にロジックを持たせない。** Rust 側はプロセスの管理だけ。ポリシーや承認を殻に書かない
- **WebSocket はトークンで守る。** 同じ PC の別のプロセスやブラウザのページが、ブローカーに承認を送れてはいけない。
  殻が起動のたびに乱数のトークンを作り、サイドカーと画面にだけ渡す
- **開発中は殻なしで動く。** `uv run benchscout serve` でコアを起動し、画面はブラウザで開く。CLI と MCP の口(素の Claude Code から使う道)もそのまま残す

### バイナリ配布で増える仕事

- OS ごとにビルドが要る(クロスコンパイルはできない)→ CI で Win / Mac / Linux を作る
- 署名:macOS は署名と公証が要り、殻とサイドカーの両方が対象。Windows も署名がないと SmartScreen に止められやすい。
  PyInstaller の exe はウイルス対策ソフトに誤検知されることがある
- サイズ:Python の実行環境に加え、エージェント SDK が同梱する CLI も入るので大きくなる(数値は実測してから記録する)
- エージェントの認証(Claude / Copilot のログインや API キー)は利用者がする。アプリに鍵を埋め込まない

### Python の中での選択

| 用途 | 選択 | 理由 |
|---|---|---|
| 版と環境 | Python 3.11+、uv、hatchling | 今のまま。`tomllib` が標準で使える |
| 固め方 | PyInstaller(第一候補)、Nuitka(比較用) | Tauri のサイドカーで実績が多い。起動時間とサイズが問題なら Nuitka を試す |
| 型と検証 | pydantic v2 | action の引数、設定ファイル、イベントのスキーマを1か所で定義し、JSON Schema にも出せる。mcp の依存として既に入っている |
| 並行処理 | asyncio(anyio) | エージェント SDK と MCP が非同期。pyserial などの同期 I/O はスレッドで包む |
| Web サーバー | Starlette + uvicorn | mcp の依存として既に入っている。新しい依存を増やさない |
| データ形式 | TOML | 標準の `tomllib` で読める(§4) |
| 品質 | pytest(今のまま)、ruff、pyright | 型付きの action やイベントを入れるので、静的チェックを足す |

### 見直す条件(ここに当たったら再検討)

- サイドカーの起動時間、サイズ、誤検知、署名の手間が許容できない → ブローカーとポートの持ち主から Rust に移す
- ロジアナなど高レートのデータで Python が遅い → その経路だけを Rust に出す
- Claude Agent SDK の Python 版が TS 版より明らかに遅れ、必要な機能が使えない

  (https://code.claude.com/docs/en/agent-sdk/overview)
- Copilot SDK は Copilot のサブスクリプション(Free を含む)で使える
- 影響:「exe で配って Claude Code を埋め込む」と、Claude Pro / Max の利用者は自分のサブスクで使えない。
  利用者が自分の Claude Code から MCP + skills でつなぐ道(AMD Ross 型)は、利用者自身が公式の製品を使うので問題ない
- 提案:**入口を2つ、同格にする**
  - 埋め込み:Copilot SDK(サブスク)、Claude Agent SDK(API キー / クラウド経由)
  - 外部エージェント:利用者の Claude Code、Cursor、VS Code などが MCP でコアにつなぐ
  - GUI は「エージェントの入れ物」ではなく **「ブローカーの操作盤」**(機器の一覧、ログ、承認、タイムライン)と位置づける。
    どちらの入口でも同じ画面で承認する
- Claude Code の名前は製品名に使えない(同じ文書)

**R2. ブローカーが複数できてしまう**

- 今は `benchscout mcp` を起動するたびに、別のブローカー(別プロセス、別の承認待ち、別のポートの持ち主)ができる
- GUI と外部の Claude Code を同時に使うと、ポートを奪い合い、GUI から外部エージェントの承認を出せない
- 提案:**1台の PC にコアは1つ。** コアが MCP を(ローカルの HTTP で)出し、外部エージェントはそこにつなぐ
  (stdio しか使えないクライアントには、コアへ中継するだけの薄い `benchscout mcp` を残す)。埋め込みのエージェントには、
  SDK のプロセス内 MCP(Claude Agent SDK の `create_sdk_mcp_server` など)でコアのツールを渡す

**R3. 承認をファイルの書き換えで偽造できる**

- 承認の状態は作業フォルダの `.benchscout/approvals.json` にあり、`status` を `granted` に書き換えれば通る
- ファイル書き込みやシェルを持つエージェントなら、`benchscout approve` を打たなくても承認を偽造できる。
  SDK の許可判定でシェルを止めても、ファイル書き込みのツールで書ける
- 提案:
  - 承認の状態はコアのメモリに置く(残すならエージェントの作業フォルダの外に置き、コアだけが書く)
  - 承認はトークン付きの UI の経路(と、人が打つ CLI)からだけ受け付ける
  - bench モードでは、埋め込みエージェントのツールを **原則禁止**(deny-by-default)にする。許すのは `bench_*` と読み取り程度
- これは今のコードの不具合でもある(§10 に追記)

### 中

**R4. 起動のたびの見立てを LLM に頼ると、遅くて高い**
- 最初の報告は1回 0.16〜0.32 ドルかかった(§9)。Copilot も1回ごとに premium request を消費する
- 一覧と見立て(異常を先頭に出す、おすすめの組み合わせ)はルールで即座に出せる。LLM は、機器を選んだ後や質問されたときから使う
- 「向こうから動く」は損なわない。最初の一声が決定的な処理になるだけ

**R5. エージェントの CLI を同梱しない**
- Python の SDK は Claude Code CLI / Copilot CLI を同梱している。それをさらに PyInstaller で固めると、サイズ、入れ子の実行ファイルの署名、
  再配布してよいか(未確認)が問題になる
- 提案:エージェントの CLI は利用者がインストールしたものを使う(SDK の CLI パス指定)。認証もそちらにある

**R6. Windows / Linux はまだ動かない**
- `LiveIo.usb_devices` は macOS(`system_profiler`)だけ。Windows の USBTMC は、pyvisa-py だと libusb のドライバ差し替えが要る
  → NI-VISA が入っていればそちらを使う
- exe で配るなら、ここが実作業になる

**R7. シェルのログとコマンドの応答が混ざる**
- MCU のシェルは、勝手にログを流しながらコマンドにも応答する。Codec は「応答」と「勝手に出る行」を分けなければならない
- プロトコル層(§4)で一番難しいところ。line-shell の Codec の要件として明記する

**R8. 承認が多すぎて疲れる**
- ネイティブ USB の listen のように、毎回承認が要る操作がある。セッション中は「このポートの listen は許可」のような、
  範囲と期限付きの許可が欲しくなる
- 「承認は1回限り」の不変条件とぶつかるので、変えるかどうかを決める

### 小

- **ポートの専有**:他のアプリ(Arduino IDE、screen)も同じポートを開ける。pyserial の `exclusive=True`(POSIX)で排他にする
- **画面に出す事実はブローカーから**:機器のカードはブローカーのデータ(根拠付き)をそのまま出し、LLM の文章は会話欄だけに出す。
  「不明は不明」を UI の側でも守れる
