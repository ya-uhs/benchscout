# benchscout 設計メモ

このプロジェクトの「なぜ」と「何を決めたか」をまとめたもの。コードを読んでも分からない前提と判断をここに残す。
**思想・方向性の正本はこのファイル。** README.md と CLAUDE.md はここの要約で、食い違ったらこちらが正しい。
方向性を変えたら、まずここ(特に §11 決定ログ)を直してから他を合わせる。

(2026-10 のチャットでの議論から起こした。最終更新 2026-10-31)

## 0. 1分で読む要約

- **何か**:PC に刺さった FPGA / MCU / 測定器を自分で偵察し、見立てを添えて「どれを見ますか?」と聞き、
  選ばれた機器の観察・診断・実機操作を、利用者のエージェントと一緒に進める **VS Code 拡張**
- **思想**:中身は skills と MCP のまま。違うのは **向こうから動く** こと(proactive + situated)
- **頭脳は利用者のエージェント**:LLM の推論、会話、ファイル操作は、利用者が使っているエージェント
  に任せる。対象は **Copilot(VS Code)、Claude Code、OpenAI 互換 API(ローカル LLM を含む。VS Code の Copilot に登録して使う)** の3つ。
  benchscout は LLM 機能を持たず、埋め込みもしない。
  エージェントとは MCP でつながる(AMD Ross と同じ形)
- **benchscout が持つもの**:偵察と見立て、機器の門番(ブローカー)、知識とプロトコル定義(データ)、
  専門家としての振る舞い(MCP の instructions / prompts、skill)、機器と承認の操作盤(VS Code のパネル)
- **入口は1つ**:利用者のエージェント + MCP。画面は VS Code 拡張。配布は .vsix(Marketplace には出さない)
- **安全**:承認は人の経路(拡張のパネル)からだけ。エージェントの経路には承認する手段がない
- **範囲**:ベンチの観察・診断・実機操作に絞る。開発ツール側へは pack を足すだけで広げられる構造にしておく
- **ハードコードしない**:コードは仕組みだけ。知識・プロトコル・手順・設定はデータファイル

## 1. 出発点:何を作りたいか

HW開発でAIを使うとき、これまでは skills や MCP を用意して、人間が「このツールを使って」「このskillでやって」と頼んでいた。
人間が指揮役(オーケストレーター)になるので、そこがボトルネックになる。

目指すのは Meta Muse や Grok Bot のような、**向こうから動く** スタイル。

- ツールを開くと、繋がっている機器を自分で探して、デバッグや調査を **提案してくる**
  - 例:「ESP32 と Xilinx FPGA(JTAG)が刺さってますよ。どれを見ますか?」
  - 例:「このデバイスは UART で反応しますよ。コマンドはこれっぽい」
- 常時監視ではない(できてもいい)。**開いた瞬間に場を偵察して報告する** のが基本
- 熟練者が机に来て、ケーブルを見ただけで状況を言い当てるイメージ

### 一番大事な結論

> **中身は skills と MCP のまま。違うのは、向こうから動いてくれること。**

技術の差ではなく、主導権がどちらにあるかの差。「HWの専門家として最初から生まれた自律エージェント」。

### Meta Muse / Grok Bot から何を取り入れるか

調べた内容(2026-10 時点、§8 の出典)から、思想ごとに採否を決めた。

| 思想 | 出どころ | benchscout での形 | 採否 |
|---|---|---|---|
| 頼まれる前に提案する | Muse | 開いたときの偵察と見立て(ルールで即座に)、提案カード | 採用(中核) |
| 隔離されたゲートを通らないと外に届かない(Sentinel) | Muse | ブローカー + ポリシー。ただし **LLM ではなく決定的なルール** で判定する | 採用(既存) |
| 機微な操作の前に必ず確認する | Muse / Grok Bot | 状態を変える操作は、人がパネルで承認する | 採用(既存) |
| 汎用の画面操作より型の決まった connector を使う | Grok Bot | 型付きの action / コマンドだけを渡し、生のポートは渡さない | 採用(既存) |
| 目標 → 計画 → 進捗、やったこと・やることの監査ログ | Muse | 「調査」単位(目標・計画・根拠・実行した操作)とパネルのタイムライン | 採用(後段) |
| 記憶(一度言ったことを覚える、忘れさせられる) | Muse | ベンチの記憶(プローブの接続先、配線、過去の所見)。人の発言は根拠「user said」として区別する | 採用(後段) |
| うまくいった手順を skill として保存する | Grok Bot | コマンド辞書やプレイブックの下書きをエージェントが作り、人が承認したら追記 | 採用(後段) |
| スケジュールやイベントで起動する(Routines) | Grok Bot | USB 挿抜やログのパターンで起きる | 保留(できてもいい) |
| 常駐し、専用の環境を持つ | Grok Bot / Muse | 前提にしない。開いている間だけ動く | 当面不採用 |
| 複数の Bot が仕事を引き継ぐ | Grok Bot | ― | 当面不採用 |

Grok Bot の弱点として指摘されている「モデルを選べない」「権限が粗い」「監査ログがない」は、benchscout は
最初から持つ(モデルは利用者のエージェントで選ぶ、操作単位の承認、承認と操作の記録)。ここが差別化点。

### 名前について

定着した一語の呼び名はない。近い用語:

- **Proactive agent**:頼まれる前に動く(Muse はこれ)
- **Situated agent**:環境に埋め込まれて知覚・行動する(ロボティクス由来)
- **Ambient agent**:常駐してイベントで動く。常時監視寄りなので少しずれる
- **Infrastructure-as-Prompts**:Octopus Protocol 論文の用語。最も近い先行研究

正確に言うなら「proactive + situated なドメイン特化エージェント」。

## 2. 振る舞いの原則(UX)

1. **開いたら偵察 → 見立て → 提案。** 人間はプロンプトを書かなくていい
2. **流れ:偵察 → 見立て付きの一覧 → 「どれを見ますか?」(1つでも複数でも)→ エージェントとの会話を始める**
   - 一覧と見立ては **ルールで即座に出す**(LLM を待たない、費用もかからない)。異常がある機器を先頭に出し、
     おすすめの組み合わせを初期選択にする
     - 例:「ESP32-S3 がリセットを繰り返しています(`rst:0xf BROWNOUT_RST`)。オシロ DS1054Z もあります。この2つで電源を見ますか?」
   - 「このデバイスを使いたい」(入力欄から絞り込む)と「どれか分からない」(一覧から選ぶ)は、同じ画面の2つの使い方
   - **複数選択が基本**。MCU + オシロ + 電源のように、組み合わせで初めてデバッグになる
   - **選んだものがセッションの範囲**。選んだ機器はコアが確保(acquire)し、ログを聞き続け、提案の対象にする。選ばれていない機器には触らない
   - 「これを見る」を押すと、用意した最初のプロンプトでエージェントとの会話が始まる。LLM を使うのはここから
3. **最初は読むだけ。** 状態を変える操作は承認制
4. **不明は不明。** 推測で名前を付けない。根拠付きの同定と推測を分ける
   - 根拠付き:`esptool` がチップ名を返した、IDCODE が一致した、`*IDN?` が答えた
   - 観察事実:CH340 がある、115200bps で `[I] sensor ok` が来る → 正体は「不明」とし、事実だけを並べる
   - 推測:「たぶん ESP8266」→ 出さない
   - 不明なものには「分かった事実」と「次に試せること」を出す
   - パネルの機器カードはブローカーのデータ(根拠付き)をそのまま出す。LLM の文章は会話欄にだけ出る
5. **名前を出すときは必ず根拠を添える。** 人から聞いたことは根拠の種類「user said」として、測った事実と区別する
6. **ソフトから見えないことは人間に聞く。** オシロのプローブがどのネットに当たっているか、どの電源がどのボードに給電しているか
7. **ユーザーの言語で話す。** 型番、パス、コマンド、ログの引用は訳さない

### 測定器

- 偵察で一緒に見つける(USBTMC / LAN / シリアル経由の SCPI、`*IDN?` で確定)
- 状態(電源の電圧・電流・出力ON)は読むだけで取れるので、最初から把握しておく
- **プローブの接続先は分からないので、聞く**
- オシロのトリガ変更のような無害に見える操作も承認制。人間が手元で見ている画面を勝手に変えない

### 波形

自前の波形ビューワーは作らない(少なくとも当面)。「ここに保存したよ」で十分。

- 保存するのは **オシロの画面キャプチャ(PNG)** と **生データ(CSV)**。保存先は開いている作業フォルダの中(エージェントが読める場所)
- エージェントの価値は **数値で報告すること**(「3V3 が 2.71V まで 3.2ms 落ちた、閾値は 2.8V」)
- じっくり見たいときは PulseView やオシロ純正ソフトで開けばいい

## 3. アーキテクチャ

### 役割分担:頭脳は利用者のエージェント、benchscout は道具と門番と操作盤

「頭脳はバックエンド」とは、**benchscout に LLM 機能を作らない** という意味。

- LLM の推論、会話、ファイルの読み書き、シェルは、利用者が使っているエージェントに任せる
- benchscout に自前のエージェントループ、LLM プロバイダの抽象化、エージェントの埋め込み(SDK)は作らない
- エージェントとは **MCP だけ** でつながる。どのエージェントでも同じ道具と同じ安全が効く
- 認証と課金は利用者のエージェントのもの。benchscout は鍵もログインも持たない
  (Claude Agent SDK を埋め込んで配る形だと、Anthropic の方針で claude.ai ログインを提供できない。§15 R1)

**決まった処理は LLM を通さない。** USB 列挙、`*IDN?`、一覧と見立ては、コアが先に済ませる
(速い、毎回同じ結果、トークンを使わない)。エージェントには結果を最初の文脈として渡す。

benchscout に残る価値は4つ:

1. **開いただけで動き出す**(偵察し、見立てを出し、最初のプロンプトを用意する)
2. **機器の門番(ブローカー)**:どのエージェントでも同じ安全ポリシーが効く
3. **専門家としての振る舞いと知識**:MCP の instructions / prompts と skill(手順、方針)、知識データ、プロトコル定義
4. **機器と承認の操作盤**:VS Code のパネル

### プロセスと経路

```
VS Code
├── 利用者のエージェント(Copilot / Claude Code / Cline …)
│       │ MCP (stdio)
│       ▼
│   benchscout mcp(中継だけ。ブローカーを持たない)
│       │ エージェントの経路(ソケット / 名前付きパイプ):ツールを呼ぶだけ。承認の手段はない
│       ▼
├── benchscout 拡張(TypeScript)── 制御の経路(子プロセスの stdin/stdout)──► benchscout-core(Python)
│     パネル:機器の一覧、見立て、ログ、承認、タイムライン               ブローカー、ポリシー、偵察、プロトコル層
│                                                                          │
│                                                                          ▼
│                                                                 実機 / 外部ツール
```

- **コアは拡張の子プロセス。** 拡張がコアを起動し、制御の経路はその stdin/stdout そのもの。鍵やトークンは要らず、
  ファイルにも環境変数にも何も置かない。拡張(=そのウィンドウ)が閉じればコアも終わり、ポートを手放す
- **エージェントの経路はツールしか持たない。** `benchscout mcp` はエージェントが起動する中継で、コアのソケットにつなぐだけ
- **機器の確保はウィンドウをまたいで排他。** VS Code のウィンドウごとにコアができるので、同じ機器を2つのウィンドウが
  同時に使わないよう、機器ごとのロック(labgrid の acquire と同じ考え)で守る。他のウィンドウが確保している機器は
  「使用中(どのウィンドウか)」と表示する(§15 S1)
- **確保したポートは OS のレベルで排他にする**(POSIX は `TIOCEXCL`、Windows の COM は元から排他)。
  エージェントがシェルから同じポートを直接開こうとしても失敗する。これが「ポートを直接触らせない」の実際の強制になる
- VS Code を使わない人(Claude Code の CLI など)のための `benchscout console`(端末の操作盤)は、同じコアの制御の経路を
  端末から使うだけのもの。後回しにする(§15 S6)

### レイヤー

```
L4  操作盤       VS Code 拡張のパネル(一覧、見立て、ログ、承認、タイムライン)。コアのイベントを表示し、人の操作を制御の経路で送る
L3  エージェントの口 MCP(`benchscout mcp` の中継 → エージェントの経路)、MCP の instructions / prompts、skill
L2  ブローカー     ポートの持ち主、ポリシー、承認、セッション範囲、機器のロック、記憶、成果物フォルダ
L1b 識別         正体+根拠を返す(アクセス層をブローカー経由で借りる)
L1a アクセス       コマンド辞書 → Codec → Transport(§4)、外部ツールのアダプタ
L0  探索         USB 列挙、シリアルポート一覧、VISA 一覧、mDNS。何も開かない
```

境界の決め方:

- **承認はブローカーで行い、人の操作は制御の経路からだけ受け付ける**(§15 R3)。エージェントを差し替えても安全は変わらない
- **人間への質問もブローカー経由**(`ask_user` のような MCP ツール)にし、パネルにボタンで出す。
  対応するクライアントでは MCP の elicitation も使えるが、それだけには頼らない
- **ポートはブローカーが持つ。** 確保したポートは OS で排他にする
- **MCP = 何ができるか**(能力+ポリシー)、**instructions / prompts / skill = 専門家ならどうするか**(手順、勘所)、
  **偵察 = コード**(決定論的)
- **振る舞いは skill で配り、最低限の約束だけ MCP の instructions にも書く**(§15 S4)。skill は Claude Code なら `.claude/skills/`、
  それ以外は `.agents/skills/` に置く。原本はリポジトリに1つ。最初のプロンプトは MCP の prompts でも出す
- **MCP ツールは汎用に保つ。** `bench_scan` / `bench_impact` / `bench_do` に加え、`bench_commands(target)`(使えるコマンドと影響度の一覧)と
  `bench_call(target, command, args)`。コマンドごとにツールを生やさない(エージェントが変わっても同じに見え、ツール数も増えない)
- **承認待ちのツール呼び出しは、人がパネルで決めるまで待つ**(期限付き)。押されたらそのまま実行し、期限が来たら「承認待ち」を返す(§15 S3)
- **通信路と外部ツールは別物。** esptool や openocd は自分でポートや USB を開くので、ブローカーが「持ち主の切り替え」をする
  (ログ配信を止める → 排他を外して手放す → ツールを実行 → 開き直す)

### データモデル:スタックではなくグラフ

USB-UART、FT2232H(JTAG+UART)、ESP32-S3 内蔵 USB(シリアル+JTAG)、ST-Link(SWD+VCP)のように、実際の繋がりはプロトコルのスタックに分けられない。

```
物理デバイス(抜き差しの単位) ──持つ──> 口(開く・占有の単位) ──プロトコル──> 相手(関心と影響の単位)
```

- プロトコル(UART / JTAG / SCPI)はノードではなく **線のラベル**
- 相手は `hosted_on` を持てる(例:FPGA の中の UART は、FPGA を書き換えると落ちる)
- 分からない線は分からないまま持てる(CH340 の先は「?」)
- 一覧は「ポート単位」ではなく「ボード単位」で見せる
- 参考:**labgrid**(Resource / Driver / Target / Strategy、リソースのロック)

### ポリシー:読む/書くではなく、状態を変えるかで分ける

| 分類 | 例 | 扱い |
|---|---|---|
| SAFE | USB 列挙、流れているログを読む、`*IDN?`、電源の電流値を読む、JTAG IDCODE 読み取り | 自動 |
| DISRUPTIVE | esptool(読むだけでもリセットが入る)、JTAG で CPU を止める、オシロの設定変更、**リセットがかかりうるポートを開く** | 承認 |
| DANGEROUS | フラッシュ書き込み、電源出力の変更、FPGA のコンフィグ | 承認+警告 |

- 影響はグラフをたどって判定する(操作 → 乱す相手 → その上で動く相手 → それらに繋がる口すべて)
- 提案には必ずポリシーの理由(`why:`)を付け、エージェントはそれを引用する(推測させない)
- 承認は人の経路からだけ出せる。DANGEROUS は (操作, 口, 引数) に紐付き1回限り、DISRUPTIVE は (操作, 口) に範囲と期限付きでも出せる(§15 R3、R8)
- ユーザー定義コマンドは影響度を宣言する。**宣言がないものは DANGEROUS 扱い**(今の「未知の操作」と同じ)

## 4. プロトコル層とユーザー定義コマンド

一般的なプロトコルは同梱するが、ユーザーが実装したコマンド(MCU 内蔵シェルなど)もある。
それを **設定ファイルだけで足せる** ようにする。難しいのはレイヤーの切り方で、次の3段に分ける。

```
コマンド辞書  名前・引数の型・影響度・応答の解析            ← ユーザー設定 / 同梱パック(データ)
     │         例: status=safe, led {idx}=disruptive, reboot=dangerous
Codec         1回のやりとりの区切り方(汎用、パラメータで調整)
     │         line-shell(プロンプト正規表現、改行、エコー除去)/ scpi / at / binary(SLIP、COBS、長さ付き)
Transport     バイトを運ぶだけ。開く・専有・多重化はブローカー
               serial(baud など)/ tcp / visa / usb
―― 別系統 ――
外部ツールアダプタ  esptool / openocd / openFPGALoader。自分でポートを開くので、ブローカーが持ち主を切り替える
```

- **ユーザーが足すのは基本的にコマンド辞書だけ。** Codec と Transport はパラメータで選ぶ。新しい Codec が要るときだけコードを書く
- **同梱プロトコルもユーザー定義と同じ形式のファイル**(SCPI 共通コマンド、AT、Zephyr shell、ESP-IDF console、U-Boot など)。
  コードに特別扱いを残さない
- **紐付けは根拠で決める。** 「この基板にこのシェルがある」は、USB の VID/PID・シリアル番号、起動バナーの正規表現、
  パネルでの人の割り当て(根拠「user said」)のどれかで決める。確かめるためのコマンドの試し打ちは、未知の UART に
  バイトを書くことになるので承認制
- **生のバイト送信(`serial.send`)は常に承認制**
- baud や改行コードなどの通信パラメータは Transport/Codec の設定に置く。コードに固定しない
- **line-shell の Codec は「応答」と「勝手に出る行」を分ける。** MCU のシェルは、ログを流しながらコマンドにも応答する。
  プロトコル層で一番難しいところ(§15 R7)
- 学習:エージェントが `help` の出力などからコマンド辞書の下書きを作り、人が承認したらファイルに追記する(Grok Bot の「手順を skill にする」に相当)

定義の例(形式は TOML 案。§12 で未決):

```toml
[protocol.myboard]
codec = "line-shell"
transport = { kind = "serial", baud = 115200 }
prompt = '^myboard> $'
line_ending = "\r\n"

[protocol.myboard.match]          # この根拠がそろったときだけ紐付ける
usb = ["1a86:7523"]
banner = 'MyBoard fw v\d+'

[[protocol.myboard.command]]
name = "status"
send = "status"
effect = "safe"
parse = { regex = 'vbat=(?P<vbat_mv>\d+)mV' }

[[protocol.myboard.command]]
name = "led"
send = "led {idx} {on}"
args = { idx = "int", on = "bool" }
effect = "disruptive"
```

置き場所は「同梱 → ユーザー全体 → 作業フォルダ」の順に重ね、後ろが優先(案)。

## 5. ハードコードしない

原則:**コードには仕組みだけ。知識・プロトコル・手順・設定はデータ。**
目標は、中核のコードに `serial` や `ESP32` のような特定の機器・プロトコル名が出てこない状態(テストで確認できる)。

今のコードで外に出すもの(2026-10-31 の棚卸し):

| 場所 | 中身 | 移す先 |
|---|---|---|
| `knowledge.py` | USB_IDS、IDCODES、LOG_SIGNATURES、基板の配線(lambda でのマッチ)、測定器の種類 | 知識データファイル。既存 DB(USB ID、openFPGALoader、udev ルール)を優先し、自前の表は補助 |
| `policy.py` の `ACTIONS`、`_ENERGIZING` | 操作ごとの影響度 | 各 action / コマンドが自分で宣言する |
| `broker._execute` | 操作ごとの if の連鎖 | Action レジストリ(名前、影響度、引数の型、実行) |
| `recon.run` | `port.kind` での分岐、`vid == 0x0403` の判定 | Probe のレジストリ |
| `recon.propose` | `"ESP32"` の文字列判定、`"3V3 rail"`、`":SINGle"` | 提案・見立てのルールのデータ |
| `cli.py` | `BACKENDS`、`OPENING_PROMPT`、`LANGUAGE_NAMES` | 最初のプロンプトは MCP の prompts とデータへ。エージェントの起動テンプレートは不要になる |
| 各所 | 115200 baud、listen 2 秒、`TOOLS` | 設定ファイル |

ただし抽象化のための抽象化はしない。2つ目の実例が出たときに仕組みにする。

## 6. 範囲と拡張:観察・診断・実機操作に絞る

## 9. 実機で学んだこと(コードに反映済み)

模擬データでは一つも出なかったものばかり。

1. **ネイティブ USB の ESP32 は、ポートを開いただけでリセットされうる**(macOS)。読んでいる最中にポートが消えて USB が再接続された。→ 開く操作を DISRUPTIVE に。消えたポートはクラッシュではなく事実として記録
2. **VISA の一覧にシリアルポート(`ASRL…`)も混ざる。** そこに `*IDN?` を送ると、未知の UART にバイトを書き込むことになる → ASRL は VISA 側で扱わない
3. **引数付き SCPI クエリ**(`MEAS:CURR? CH1`)を書き込み扱いしていた → コマンドのヘッダで判定
4. **Tang Nano 9K が認識されない原因はケーブル**(充電専用)。USB に出てこないものはソフトからは何も見えない → skill に「疑う順番」を追加
5. **Sipeed の BL702 は FT2232H のふりをする**(0403:6010)。シリアル番号 `FactoryAIOT Pro` は全個体で共通
6. **自前の IDCODE 表が間違っていた**(0x0100481B は GW1N(R)-9C)。→ openFPGALoader 自身のデータベースを優先し、根拠にどちらで判定したかを書く
7. **openFPGALoader を ESP32 の USB-JTAG に向けていた** → FTDI 互換の JTAG だけに限定
8. 費用:最初の報告は1回あたり約 0.16〜0.32 ドル(定価換算)。大半は Claude Code 本体の前提文脈の読み直し → 一覧と見立てはルールで出す(§2)

## 10. 実機で見つかり、原因は分かったが未修正のもの

1. **`serial.listen` の `arg=9600` が 120 秒以上返らない。** `broker._execute` が `arg` を **秒数** として `float(arg)` している
   (9600 秒待っていた)。baud は `recon.listen_into` で 115200 に固定で、変える手段がない。
   → Action レジストリで引数に型を付け(秒と baud を分ける)、MCP の docstring にも書く
2. ~~`port="/dev/cu.usbmodem1101"` だと黙って失敗する~~ → 直した(2026-10-31):id でもパスでも引け、分からなければ id とパスの一覧を返す
3. **Tang Nano のファブリック UART が既定のレートで無音。** 上の 1 のせいで baud を変えて試せず、baud か bitstream かは未切り分け
4. ~~承認をファイルの書き換えで偽造できる~~ → 直した(2026-10-31):承認はコアのメモリだけ。`audit.jsonl` は記録で、書き換えても何も許可されない(§15 R3)

## 14. 技術スタックと配布

### 決めたこと

- **配布は .vsix**(Marketplace には出さない)。中に **Python のコアを PyInstaller で固めた単体バイナリ** を同梱する
- **拡張は TypeScript**(VS Code の拡張は Node の上で動くので、Node を同梱する必要はない)
- **コアは Python のまま**

### コアを Python のままにする理由

| 層 | 必要なもの | Python | TypeScript(拡張の中) | Rust |
|---|---|---|---|---|
| ハードウェア | シリアル、VISA、USB 列挙、esptool など | ◎ pyserial、pyvisa-py(純 Python、NI-VISA 不要)、esptool 自体が Python、pytest-embedded、labgrid | △ serialport はネイティブモジュールで拡張に入れにくい。VISA は実用的なものがない | △ serialport はある。VISA は NI-VISA が必要 |
| MCP サーバー | エージェントの口 | ◎ 公式(使用中) | ◎ 公式 | ○ rmcp |
| 数値処理 | 波形を数値で報告する | ◎ numpy | △ | △ |
| 既存資産 | 約 1250 行 + テスト | ◎ そのまま | × 書き直し | × 書き直し |

置き換えにくいのはハードウェアの層(特に VISA と esptool)で、ここは Python がほぼ唯一の選択肢。
画面は VS Code の Webview なので、言語の選択に影響しない。

### .vsix にする上での仕事

- **OS と CPU ごとに .vsix を作る**(VS Code はプラットフォーム別の .vsix に対応:`vsce package --target darwin-arm64` など)。
  PyInstaller はクロスビルドできないので、CI で OS ごとに作る
- **署名と誤検知**:拡張が起動する実行ファイルに macOS の Gatekeeper や Windows の SmartScreen がどう効くかは、
  .vsix の入れ方(ブラウザで落としたか)で変わりうる。実機で確かめてから決める(§15 S5)。PyInstaller の exe はウイルス対策ソフトに誤検知されることがある
- **更新**:Marketplace を使わないので自動更新はない。新しい .vsix を入れ直す。拡張が新しい版を知らせる程度は後で考える
- **外部ツール**(openFPGALoader、openocd など)は同梱せず PATH から探す。esptool は Python なので同梱できる

### Python の中での選択

| 用途 | 選択 | 理由 |
|---|---|---|
| 版と環境 | Python 3.11+、uv、hatchling | 今のまま。`tomllib` が標準で使える |
| 固め方 | PyInstaller(第一候補)、Nuitka(比較用) | 起動時間とサイズが問題なら Nuitka を試す |
| 型と検証 | pydantic v2 | action の引数、設定ファイル、制御の経路のメッセージを1か所で定義し、JSON Schema にも出せる(拡張の TS の型もそこから作る)。mcp の依存として既に入っている |
| 並行処理 | asyncio(anyio) | MCP が非同期。pyserial などの同期 I/O はスレッドで包む |
| 制御の経路 | stdin/stdout の JSON(行区切り、JSON-RPC 形式) | 子プロセスのパイプなので、ネットワークもトークンも要らない |
| エージェントの経路 | Unix ドメインソケット / Windows の名前付きパイプ | 利用者だけが読み書きできる。MCP の中継がつなぐ |
| データ形式 | TOML | 標準の `tomllib` で読める(§4) |
| 品質 | pytest(今のまま)、ruff、pyright | 型付きの action やメッセージを入れるので、静的チェックを足す |

### 見直す条件(ここに当たったら再検討)

- コアの起動時間、サイズ、誤検知が許容できない → ブローカーとポートの持ち主から Rust に移す(制御の経路がプロトコルなので差し替えられる)
- ロジアナなど高レートのデータで Python が遅い → その経路だけを Rust に出す

#### R3 の詳細:承認は人の経路からだけ

参考にした OSS:**ssh-add -c + ssh-askpass**(鍵を使うたびに別の画面で人に確認させ、鍵を使いたいプロセスはその画面を操作できない)、
**gpg-agent + pinentry**(パスフレーズは別プロセスの画面が受け持ち、頼んだ側には渡らない)。

- 経路を2つに分ける。エージェントの経路(MCP の中継)はツールを呼ぶだけで、承認する手段がない。
  制御の経路(承認、拒否、機器の選択)は、コアを子プロセスとして起動した拡張だけが持つ(stdin/stdout なので鍵も要らない)
- 承認の状態はコアのメモリだけに置く。記録(監査ログ)はファイルに追記するが、書き換えても承認にはならない
- 今の `benchscout approve <id>`(別プロセスからファイルを書く方式)は廃止する

**脅威モデル**:守る相手は、エージェントの **間違いと行き過ぎ**(勝手に承認する、ファイルを書き換える、ポートを直接開く)。
同じ利用者の権限で意図的に攻撃してくるプログラムは対象外(OS の利用者の境界がない以上、防ぎきれない)。
DANGEROUS な操作には、将来 OS の確認(Touch ID など)を挟む余地を残す。

**残る穴**(R1 で利用者のエージェントを使うことにしたため、エージェントのツールを止められない):

- 選んでいない機器は OS の排他がかかっていないので、エージェントがシェルから直接開けてしまう。ここは instructions / skill での指示だけ
- エージェントが自分で `benchscout console` を起動し、その制御の経路に入力を流し込めば承認を偽造できる。
  意図的な回避なので脅威モデルの外とするが、console は端末(TTY)からの起動に限り、監査ログに制御元を残す
- Claude Code 向けの設定(`benchscout setup`)では、`benchscout` 自体を Bash から呼ぶことを permissions の deny に入れておく

#### R8 の詳細:範囲と期限付きの許可

- **DISRUPTIVE な操作に限り**、(操作, 口) に対して「このセッションの間」または「N 分間」の許可を出せる
  (例:ネイティブ USB の `serial.listen` を、選んだ機器を見ている間は毎回聞かない)
- **DANGEROUS な操作は今までどおり**、(操作, 口, 引数) に紐付いた1回限り
- 範囲付きの許可も、出せるのは制御の経路(人)だけ。選択から外れた機器、セッションの終了、期限切れで消える
